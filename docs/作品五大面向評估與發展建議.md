# Taipei Maze｜作品五大面向評估與發展建議

更新日期：2026-11-07。用途：團隊決策、實作排序、競賽答辯與後續試辦討論。

本文將使用者提出的「考靠性」按「可靠性」理解，從可行性、功能性、可靠性、易用性、亮點／巧思五個面向，延伸分析價值、限制、改善方式與驗證證據。本文屬於分析與候選建議，不代表新增功能已獲排入開發，也不代表實測通過。

## 1. 評估基準與整體判斷

- 七語固定為繁體中文、英文、越南文、印尼文、泰文、韓文、日文；語音為預生成音檔，執行期不呼叫 LLM、翻譯或 TTS API。
- 新資源遵守非中國來源與授權審查；本次僅修改文件，沒有新增依賴、素材或外部服務。

- 本文是 repo 內部資料的分析，不是競品調查、現地勘查、使用者研究或最新官方評分規則的重新查核。

### 1.3 五面向結論

| 面向 | 設計判斷 | 最大缺口 | 最有效的下一份證據 |
| --- | --- | --- | --- |
| 可行性 | 局部示範可行；全站服務須分期 | 場域核對、QR 設置與維護責任 | 一個連續區域、兩組起訖點的完整流程 |
| 功能性 | 任務流程完整，恢復流程有價值 | 核心模組尚待串接 | 新起點能重新計算，而非固定播放頁面 |
| 可靠性 | 保守限制與版本設計良好 | 資料真實性、方向與跨平台實證 | 一般、無障礙、無路線、重掃四類測試 |
| 易用性 | 能降低讀圖與語言負擔 | 入口發現、朝向確認、操作負擔 | 初次使用者不經講解完成任務 |
| 亮點／巧思 | 易懂選路與迷路恢復有辨識度 | 差異尚待可視化與量測 | 同起訖的路線取捨與可解釋差異 |

不先給 90 分或五星：目前缺少共同評分尺度與實測，數字會讓「設計潛力」被誤認為「成品完成度」。

## 2. 可行性：從能做出來到能持續服務

### 2.1 技術可行性

局部路網、QR 固定點、TypeScript Dijkstra、SVG 地圖與本地音檔可以分開實作，再以同一個 NavigationPlan 串接。P0 不依賴連續定位或執行期雲端 AI，有助控制系統邊界。

目前 Vue 基底能承接頁面與狀態管理；應先隔離導航 domain、bridge adapter、資產載入與 UI，再刪減不需要的範例。不能直接把原有票券、繳費或周邊服務頁算入本作品功能。

| 工程問題 | 可行處理方式 | 仍須實證 |
| --- | --- | --- |
| 缺少可用路網 | 先建合成 fixture，再建立局部核對路網 | 每條邊、方向、設備、樓層及指令 |
| 宿主依賴過多 | 只使用主流程需要的掃碼能力 | 不依賴帳號或 GPS 也能完成 |
| 首次離線載入 | 先確認宿主本地封裝／載入路徑 | 新安裝、未預載、關網啟動 |
| 多語與音訊工作量 | 凍結 key 與 24 句，再批次生成、逐語審查 | 168 核心音檔與必要 UI 齊備 |
| 跨平台差異 | 早期用同一最小流程在兩平台驗證 | 返回、掃碼取消、音訊、背景恢復 |
| 功能與資料耦合 | 使用版本化資料包與清楚模組介面 | 換 fixture 不需改動頁面邏輯 |

### 2.2 資料可行性

研究資料包適合作為 POI、出口及設備核對輸入，不是現成 Graph。最耗時間的工作可能是確認「這兩個點能不能走、以什麼條件走」，而非演算法本身。

建議逐段建立「起點照片或圖面依據 → 可通行區域 → 決策點 → 地標 → 跨層設備 → 終點」核對表。照片只有在來源、拍攝許可與再散布權利確認後才可納入交付；不要為了完整而先把未核准圖像放進 repo。

必須區分：同名設施不一定同一設備；同層不等於互通；GPS 點不等於入口；圖示存在不等於目前可用；維修排程不等於即時故障資訊。

### 2.3 場域與營運可行性

| 議題 | 試辦前要有的答案 | 尚未取得答案時 |
| --- | --- | --- |
| QR 設置 | 哪個管理單位同意、貼在哪裡、誰安裝 | 只在受控展示使用，不擅自張貼 |
| 標牌維護 | 誰巡查、誰補貼、如何停用錯誤碼 | 不對外承諾長期有效 |
| 路網維護 | 施工、店家變更、通道封閉由誰核對 | 公開範圍與核對日期，不稱即時 |
| 問題處理 | 何種錯誤須立即停用路段或整包 | 先定義保守停用與回復程序 |
| 版本發布 | 誰審查資料、誰簽核、誰回滾 | 不允許未核對包直接變正式包 |
| 主辦移交 | 誰接收程式、資料、建置文件與維護責任 | 保留未完成清單，不只交展示影片 |

### 2.4 成本與時程可行性

不要只估伺服器成本。總投入應包含前端開發、路網整理、現地核對、七語校對、語音製作、設備測試、QR 製作與巡查、來源審查，以及每次資料改版的回歸測試。

可用下列工作量模型規劃，不填沒有依據的金額：

```text
首次投入 = 開發 + 場域建模 + 翻譯審查 + 音訊製作 + 雙平台驗證 + 設置協調
持續投入 = 內容更新 + 標牌巡查 + 問題分流 + 回歸測試 + 發布維護
```

24 小時展示宜固定 SPEC 的局部範圍，優先交付兩組起訖、一次跨層、一次重掃、一般／無障礙差異。P1 搜尋與候選路線只在 P0 穩定後加入，七語要求不自行下修。

### 2.5 擴大服務的順序

1. 合成場景：驗證演算法、資料格式與錯誤處理，明確標為示意。
2. 局部核對場景：固定區域與路線，取得資料及方向證據。
3. 受控試辦：有管理單位窗口、設置同意、維護與停用程序。
4. 相鄰區域擴充：逐區處理付費區、營業時段、設備與營運單位差異。
5. 其他公共場域：重用引擎與格式，但重新建模、校對、審查；不可只替換背景圖。

## 3. 功能性：功能是否完成使用者任務

### 3.1 核心價值鏈

| 使用者要完成的事 | 產品能力 | 完成的判斷 | 常見假完成 |
| --- | --- | --- | --- |
| 知道自己在哪 | QR 驗證、位置與樓層確認 | 不同有效碼映射到正確 anchor | 任何碼都顯示同一位置 |
| 知道自己朝哪走 | 起始地標與朝向確認 | 不同進入方向得到一致可用指引 | 掃碼後直接猜左右 |
| 找到要去的地方 | 大卡片；P1 多語搜尋 | 選到實際可用 POI | 名稱存在但沒有可達節點 |
| 找到走得到的路 | 硬限制後計算路徑 | 不走被排除的邊；無路線則明示 | 無障礙只是切換顏色 |
| 看懂下一步 | 箭頭、地標、短句、音訊 | 同一 plan、同一步驟的一致呈現 | 語音、地圖、文字各自寫死 |
| 完成跨層 | 設備、目標樓層與確認 | 確認後才推進跨層狀態 | 切圖就當使用者已到樓層 |
| 迷路後繼續 | 重掃、失效舊計畫、重算 | 新起點產生可用新 plan | 重設畫面但仍播舊指令 |
| 知道已抵達 | 有效目的地確認 | 依手動或有效 QR 確認完成 | 看完動畫就自動抵達 |

### 3.2 功能廣度與深度的取捨

4 個真正可達目的地，比 40 個只有名稱的目的地更有展示價值。兩條經過核對的不同路線，比五張相同路線卡更有意義。語言切換應涵蓋錯誤與恢復畫面，不能只翻首頁。

驗收以「任務是否完成」為單位，而非頁面數、API 數、圖示數或程式碼行數。所有新增頁面都應能說明它在核心流程中解決哪個障礙。

### 3.3 情境覆蓋

| 情境 | 必須回應的需要 | 優先證明 |
| --- | --- | --- |
| 外籍旅客找出口 | 語言、出口編號、現場中文標示對照 | 切語言後目的地與路線不變 |
| 初次到站者找廁所 | 不需懂全站地圖、不強迫輸入文字 | 大卡片直接完成選擇 |
| 輪椅／推車需求 | 樓梯排除、設備限制、未知不當可用 | 無障礙路徑或明確 NoRoute |
| 不熟悉手機者 | 少層級、明顯重播與恢復 | 不必進設定才知道怎麼繼續 |
| 走錯到另一個定位點 | 接受新的有效起點、重算 | 顯示新位置，舊 plan 失效 |
| 相機被拒絕 | 解釋與可取消的恢復 | 保留原流程，不虛構定位 |
| 沒網路或缺音檔 | 正確揭露可用能力 | 文字圖像保留，不能假稱完整離線通過 |

### 3.4 功能邊界

「容易理解」是規則評估的候選排序，不是醫療或認知能力判定。「最近廁所」必須以可達路徑成本為依據；無精確距離時不偽稱公尺最近。「最快」需符合 SPEC 時間模型門檻。「無障礙路線」須說明已核對條件，不代表所有身體需求都適用。

緊急疏散、人流避堵、即時設備正常、全天候通行、全站覆蓋與連續追蹤目前均不應列為現成功能。

## 4. 可靠性：可信資料、正確計算與錯誤恢復

### 4.1 可靠性的六個層次

| 層次 | 要防止的失敗 | 建議控制 |
| --- | --- | --- |
| 資料 | 錯連樓層、未核對方向、失效設備 | schema、來源、現地核對、有效版本 |
| 演算法 | 走入禁止邊、循環、無解誤報有解 | 硬限制先過濾、合成 fixture、路徑不變量測試 |
| 狀態 | 新位置配舊路線、切語言播舊句 | session revision、原子更新、舊結果失效 |
| 平台 | 掃碼取消、返回、背景恢復異常 | Android／iOS WebView 實測矩陣 |
| 發布 | 混版資產、壞包上線、不可回滾 | 完整包驗證、版本綁定、保留上一個核准版本 |
| 營運 | QR 移貼、施工、資料久未核對 | 巡查、停用、揭露範圍與日期 |

### 4.2 主要風險表

以下「高／中」為團隊工作優先級判斷，不是已量測的發生機率。

| ID | 風險與影響 | 優先級 | 預防與恢復 | 所需證據 |
| --- | --- | --- | --- | --- |
| R01 | 起點朝向錯，左右指令反轉 | 高 | 使用方向相關的地標確認；未知不開始 | 各有效出發方向人工核對 |
| R02 | 不同營運區 B2 被直接相連 | 高 | 分區與 connector 明確建模 | 邊來源及現場連通核對 |
| R03 | 無障礙使用 unknown 設備 | 高 | 保守排除；無路線不放寬條件 | 可及性與故障 fixture |
| R04 | QR 是合法碼但遭移貼 | 高 | 顯示地標供比對、巡查與停用 | 錯位情境與標牌管理流程 |
| R05 | 重掃後語音仍播放舊路線 | 高 | 先停播、失效舊 plan，再提交新版本 | 快速重掃與晚到回覆測試 |
| R06 | 只測暖快取，首次離線失敗 | 高 | 分開測首次關網與已預載關網 | 全新安裝紀錄與資產清單 |
| R07 | 舊 bridge 逾時回覆被當新結果 | 高 | 同名請求串行；逾時不立即重送 | 取消、逾時、延遲回覆案例 |
| R08 | 翻譯、音檔與圖示意思不同 | 高 | 共用 key／版本，逐語逐句審查 | 翻譯與音訊對照表 |
| R09 | 維修快照被說成即時狀態 | 高 | 顯示時間、來源與限制 | UI 文案與資料更新紀錄 |
| R10 | 部分新檔配部分舊檔 | 高 | manifest 驗證整包，不相容不啟用 | 中斷載入與 hash 失敗測試 |
| R11 | HTTP 200 被當成功部署 | 中 | 另查 build、資產、深連結與核心流程 | 功能 smoke 與版本核對 |
| R12 | 地圖載入錯卻繼續給方向 | 高 | 停止導航並提供重試／求助 | 圖檔缺失及變換錯誤案例 |

hash 只能驗證資料是否符合預期 bytes，不能證明路線符合現況，也不能防止合法 QR 被實體移貼。簽章或 hash 與現場巡查解決不同問題。

### 4.3 最低驗證矩陣

- 演算法：可達、不可達、單向、封閉、未知可及性、跨層、一般／無障礙、同起終點。
- 定位：有效碼、他站碼、未知 anchor、停用碼、版本不符、過長資料、任意 URL、取消。
- 一致性：掃碼連按、切語言、切模式、返回、背景恢復、音訊晚到、新定位重算失敗。
- 資產：缺地圖、缺翻譯、缺音檔、錯 hash、混版、首次離線、清除快取後啟動。
- 平台：至少依 SPEC 的 Android／iOS 真機矩陣記錄；一般瀏覽器與 Simulator 不取代真機掃碼。
- 主流程：至少兩組起訖，連續三次，以及 30 分鐘壓力操作，依 SPEC 留存結果。

### 4.4 發布與維護可靠性

目前 Docker build 階段呼叫 `pnpm build-only`，與 package 中另外執行型別檢查的 `build` 不同；不應把容器成功建置當成型別檢查已通過。既有 CD 健康檢查只確認首頁 HTTP 成功，尚不能證明導航、音訊與 bridge 正常。這是原始碼檢視發現，本次未執行部署驗證，也未修改 workflow。

候選改善：正式發布前獨立執行型別與核心測試、記錄 image／build commit、核對資料包版本；為不存在的資產設定正確錯誤回應，避免 SPA fallback 把 HTML 當 JSON／音檔；保留可恢復的已核准版本。細節應另作實作計畫，不把本文當已完成設定。

## 5. 易用性：從發現入口到迷路恢復

### 5.1 使用旅程中的負擔

| 時刻 | 使用者可能卡住的事 | 建議改善 | 如何觀察 |
| --- | --- | --- | --- |
| 還沒開啟服務 | 不知道城市通裡有這個功能 | 清楚服務名稱、QR 旁提供使用方式 | 是否能自行找到入口 |
| 掃碼前 | 看不懂提示、鏡頭對不準 | 圖示、短句、取消與權限恢復 | 首次成功掃碼與求助次數 |
| 掃碼後 | 知道樓層但不知道朝向 | 對照現場地標後再開始 | 是否能正確指出第一個方向 |
| 選目的地 | 不知道正式名稱 | 圖示卡片、用途分類、原文名稱 | 是否能不用鍵盤選到目標 |
| 選路線 | 不懂易懂分數 | 顯示轉彎、換層、地標的實際差異 | 是否能說明選擇原因 |
| 走路中 | 被資訊塞滿或要一直看螢幕 | 一次一動作、決策點切步驟 | 錯過決策點及重播次數 |
| 轉乘設備 | 不知道哪個電梯、到哪層 | 設備標籤、目的樓層與出口方向 | 是否選對設備與樓層 |
| 走錯 | 怕操作會弄壞路線 | 明顯「我迷路了」、保留目的地與需求 | 能否自行重新定位 |
| 抵達 | 不確定是不是同名另一處 | 名稱、樓層、入口／地標對照 | 是否正確確認抵達 |

### 5.2 多語不只是翻譯

七語選單應用各語言原文，避免使用者先讀懂英文才能換語言。現場中文標示與出口編號保留作對照；英文畫面不能把現場唯一中文標示完全隱去。

泰文、越南文組合符號、日韓字形及較長的翻譯都要在真機檢查。錯誤、權限、無路線、音訊失敗與資料說明也在必要翻譯範圍。單一圖示並不保證跨文化理解，應與簡短文字搭配。

切語言只更新呈現，不重設目的地、路線、步驟或無障礙偏好。靜音與重播必須明顯，不能把所有資訊藏在聲音裡；缺音檔時保留文字圖像並揭露狀態。

### 5.3 易讀與可及性

- 簡易模式減少資訊與同時可選動作，不只放大字；標準模式仍可查看整體路線。
- 不只靠顏色區分樓層、路線或錯誤；配合文字、圖示與形狀。
- 大字後仍可捲動與操作，重要按鈕不被底部列、鍵盤或安全區遮擋。
- 按鈕有可理解名稱；圖示提供輔助標籤；狀態更新與焦點順序另做讀屏測試。
- 「下一步」代表使用者確認進度，不能當成位置感測；「上次確認位置」與「目前步驟」分開呈現。
- 不宣稱服務已適用全盲者；缺少連續定位、環境障礙感知與專門驗證時，使用限制必須誠實說明。
- 不以兒童、國籍或年齡自動推論能力；讓使用者自行選擇語言與資訊密度。

### 5.4 可用性研究設計

先做小規模形成性測試找問題，樣本數由招募與時間決定，不編造代表性。成人志願者採匿名代碼；涉及兒童時先另訂適當的參與、同意與陪同安排，不把招募兒童當競賽必要工作。

比較任務可使用平面圖與本產品，但需交錯順序或使用相近不同路線，避免第二次已熟悉路線的效應。記錄裝置、語言、需求、任務、是否接受協助與失敗原因。禁止把所有參與者一起算平均，掩蓋某語言或特定需求的失敗。

| 指標 | 定義／計算 | 解讀限制 |
| --- | --- | --- |
| 無協助完成率 | 無研究員代操作而完成的人次／嘗試人次 | 需揭露任務與樣本，不能外推全站 |
| 首次定位時間 | 服務可操作至確認有效位置 | 分開記錄入口搜尋與相機權限時間 |
| 首步方向理解 | 能否指出第一段正確方向 | 不是全程不迷路的替代指標 |
| 錯誤決策次數 | 預先定義決策點的錯誤選擇 | 需有觀察紀錄，不能只由點擊推定 |
| 恢復成功率 | 發生指定迷路情境後成功重定位並繼續／嘗試 | 合成情境與實地情境分開 |
| 求助次數 | 研究員／工作人員實際介入次數 | 不將合理求助視為使用者失敗 |
| 主觀理解難度 | 任務後同一題與同一尺度回覆 | 樣本少時列原始分布，避免誇大統計 |

所有目標值應在測試前約定，測試後填實測值；沒有紀錄時填 not_run，不寫「大幅提升」或降低某個百分比。

## 6. 亮點／巧思：可解釋、可恢復、可移轉

### 6.1 已有設計最值得展示的亮點

| 亮點 | 對使用者的價值 | 有說服力的展示 | 不可過度宣稱 |
| --- | --- | --- | --- |
| 易懂路線 | 用少轉彎、少岔路與地標降低決策負擔 | 同起訖兩條不同路線，列出實際差異 | 規則分數已證明認知成本或迷路率 |
| 迷路恢復 | 走錯後可重新出發 | 換一張 QR，路線與語音同步改變 | 掃碼之外持續知道位置 |
| 七語離線指引 | 減少語言與執行期網路依賴 | 同一步驟換語言並播對應本地音檔 | 所有翻譯均已專業審查 |
| 無障礙硬限制 | 可走條件優先於排序分數 | 排除樓梯，設備不可用則換路或 NoRoute | 所有身體需求與即時狀態皆涵蓋 |
| 有限多語搜尋 | 不同叫法找到同一真實設施 | 廁所／toilet／restroom 對應同一 POI 類別 | 任意對話理解或完整 AI 助理 |
| 同一引擎不同場域 | 降低後續重作程式的成本 | 替換經驗證資料包，保留核心流程 | 任何場域都不用現勘即可部署 |

| ID | 候選巧思 | 具體使用時刻與價值 | 成本／依賴 | 建議階段 |
| --- | --- | --- | --- | --- |
| I01 | 出發地標確認卡 | 掃碼後先對照一個看得見的標誌，確認出發方向 | 方向相關地標與人工核對 | 既有 P0 朝向設計的呈現延伸 |

| I07 | 設備不可用捷徑 | 現場發現電梯不能用，僅本次 session 避開 | connector 對應與重算 | 既有例外流程延伸 |
| I08 | 非即時狀態說明 | 顯示最後核對日及資料範圍，協助判斷信任 | SourceRecord 與 UI 文案 | 既有來源呈現延伸 |
| I09 | 示範與實地模式明確標示 | 防止合成地圖被誤當實際導航 | release gate 與明顯標記 | 展示前應具備的界線 |
| I10 | 路線學習預覽 | 出發前看幾個主要決策地標，再回到一步一圖 | 避免增加首頁選項與資訊負擔 | 後續可用性驗證候選 |
| I11 | 自選提醒密度 | 熟悉者少提示、初次者逐步提示 | 新偏好及測試，不能刪掉必要安全資訊 | 後續候選 |
| I12 | 手動回到上一則指引 | 使用者想重新理解剛才的地標 | 區分查看舊指引與變更位置 | 後續候選 |
| I13 | 快速自查離線包 | 出發前顯示地圖、文字、音訊是否齊備 | manifest 驗證及新安裝情境 | P0 載入驗證的呈現延伸 |
| I14 | QR 維護對照表 | 管理者按點位編號巡查、停用與補貼 | 管理單位、標牌版本、維護責任 | 場域試辦階段 |
| I15 | 本地問題回報草稿 | 使用者暫記哪一步不清楚，離線仍可保留草稿 | 需另訂同意、保存與清除政策 | 後續；不改現行 session 清除契約 |
| I16 | 參數化場域套件 | 醫院、校園等沿用引擎與驗證工具 | 每場域重新核對、權利與維護 | 賽後擴充 |

| I18 | 檢查「不該推薦」的路線 | 主動驗證系統能拒絕不安全／不可走組合 | 負面 fixture 與產品限制定義 | 核心可靠性工作 |

問路卡只供使用者自行展示；不自動發送 Slack、Email、訊息或位置。任何照片、真人聲音、字型、模型或新增套件都須先通過既有來源與權利審查。

### 6.3 發想篩選原則

先問五件事：是否直接改善核心任務、是否能說明失敗行為、是否有可靠資料、是否能在雙平台驗證、是否排擠 P0。優先選同時增加「理解」與「恢復」的低依賴改善。

當前不建議為競賽新增連續定位硬體、即時人流、runtime AI 對話、360 環景、大型模型或全站地圖編輯器。它們需要新的資料、依賴或營運前提，無法以名稱本身證明公益價值。

## 7. 五面向之間的衝突與取捨

| 看似有利的選擇 | 可能傷害的面向 | 取捨建議 |
| --- | --- | --- |
| 增加更多目的地 | 可行性、可靠性 | 先保證可達與方向正確，再擴量 |
| 每一步都要求掃碼 | 易用性、場域維護 | QR 供確認與恢復，不要求每段連續追蹤 |
| 所有提示塞進同畫面 | 易用性 | 主畫面只放當下動作，其餘可展開 |
| 自動替使用者切路線 | 功能一致性、信任 | 變更需求或路線時清楚確認，不靜默降級 |
| 缺資料時仍給答案 | 可靠性 | 明確 NoRoute 或 guidanceUnavailable |
| 更炫的語音與動畫 | 可行性、操作速度 | 先完成文字圖像一致與可重播 |
| 為了加速而跳過七語校對 | 功能性、可信度 | 凍結範圍；未達標明列未完成，不假稱通過 |
| 為增加亮點稱為 AI | 可解釋性與答辯可信度 | 清楚說明規則與詞典，ML 留待資料足夠 |
| 直接上正式場域 | 營運可靠性 | 先取得同意、核對與維護窗口 |

## 8. 實作排序與決策點

本節是建議工作順序，非新工期承諾；P0／P1 仍依 SPEC。

| 順序 | 工作 | 開始條件 | 通過證據 | 未達時處置 |
| --- | --- | --- | --- | --- |
| 1 | 固定示範區與資料來源 | 明確範圍與負責人 | 範圍圖、來源、核對狀態 | 使用標示清楚的合成 fixture |
| 2 | 最小橋接與離線載入探索 | 宿主與裝置可用 | 真機掃碼／取消、載入方式紀錄 | 不宣稱城市通整合或完整離線完成 |
| 3 | 純路徑引擎與驗證器 | 有 fixture 與 schema | 可達／不可達／無障礙測試 | 停新增頁面先修核心 |
| 4 | 第一組完整主流程 | 路徑、指令、資料同版 | 掃碼至抵達與重定位 | 不擴 POI |
| 5 | 第二組與負面情境 | 第一組穩定 | 不同起訖、無路線、錯碼與故障 | 列出失敗，不做固定動畫替代 |
| 6 | 七語、音訊與簡易模式 | key、24 句與主流程凍結 | 七語必要 UI 與 168 音檔核對 | 依 SPEC 記錄未達標 |
| 7 | 雙平台與離線回歸 | 各平台與資產包就緒 | GATE-01 至 GATE-07 對應結果 | 未通過不稱 Demo Ready |
| 8 | P1 候選路線與搜尋 | P0 穩定且有剩餘資源 | GATE-08 與差異說明 | 保留已完成 P0，不拖入半成品 |

建議責任分工至少有：場域與資料核對、路徑與狀態、介面與可及性、多語音訊、宿主與測試、發布與文件。這些是責任角色，可由同一人兼任；交接產物與覆核人需明確。

## 9. 展示與答辯策略

### 9.1 120 秒的證據排序

| 時間 | 展示內容 | 證明的面向 |
| --- | --- | --- |
| 0–15 秒 | 用一句具體問題呈現「看圖仍不知道下一步」 | 易用性、公益價值 |
| 15–35 秒 | 城市通內掃有效 QR、確認位置與朝向、選目的地 | 可行性、功能性 |
| 35–60 秒 | 一步一圖與跨層；有 P1 才展示候選差異 | 功能性、巧思 |
| 60–80 秒 | 切語言與簡易模式，同一步驟播放本地音訊 | 易用性、一致性 |
| 80–105 秒 | 掃另一個定位點，重算並停止舊語音 | 可靠性、恢復能力 |
| 105–120 秒 | 揭露示範範圍、實測平台與下一階段 | 可行性、可信度 |

這是團隊展示建議，不是主辦規定。五面向是本文分析架構，不能冒稱官方五項評分或另配官方權重。比賽時限與評分以最新主辦公告及既有競賽文件核對；本次沒有重新查核官網。

### 9.2 可能被問到的問題

| 問題 | 應回答的核心 | 應帶的證據 |
| --- | --- | --- |
| 為什麼不用一般地圖？ | 本作聚焦局部室內、樓層、通行需求與逐步理解 | 一條完整使用者任務，不宣稱競品完全沒有類似功能 |
| 為什麼選 QR？ | 低部署複雜度的固定點確認，限制是不能連續定位 | QR 對照、朝向與重掃示範 |
| 怎麼知道使用者走錯？ | 不會自動知道；由使用者重掃確認 | 新定位與 plan 更新紀錄 |
| 易懂是主觀的嗎？ | 現版是可解釋規則，權重需用實測修正 | 特徵、候選差異與測試設計 |
| 真的是最快嗎？ | 沒有合格時間模型時不啟用最快 | 時間門檻與降級文案 |
| 電梯壞了怎麼辦？ | 本次可避開回報設備重算，沒有替代就 NoRoute | 設備不可用 fixture；不稱官方即時資訊 |
| 沒網路能用嗎？ | 說明本地封裝方式及實際測過的冷啟動條件 | 新安裝關網影片與資產版本 |
| 七語準確嗎？ | 提供審查範圍、原文對照及未完成項 | key／音檔清單、逐語審查紀錄 |
| 誰會維護？ | 試辦需有管理單位窗口、版本與巡查程序 | 維護責任表；未合作就誠實說明 |
| 可以立即全站上線嗎？ | 局部原型需逐區核對後才擴大 | 範圍、已核對路段與 gate 清單 |

### 9.3 三種可使用的定位句

- 面向使用者：「掃碼確認位置，用看得懂的下一步，找到走得到的路。」
- 面向評審：「把通行條件、地標理解與迷路恢復整合在城市通內，以可驗證的局部場景證明服務價值。」
- 面向場域管理者：「以可維護的定位點與版本化路網，先試辦一個範圍明確、能停用與回復的指引服務。」

避免宣傳句：全北車即時導航、零迷路、最安全路線、任何人都適用、完全離線已完成、AI 自動理解所有需求。

| 評估面向 | 最小證據包 | 建議負責角色 |
| --- | --- | --- |
| 可行性 | 示範範圍、工作量與依賴、宿主整合、試辦前提 | 整合／場域 |
| 功能性 | 需求追溯、兩組起訖、一般／無障礙、重掃與抵達 | 核心／前端 |

| 易用性 | 任務腳本、匿名觀察、語言與模式結果、已修問題 | UI／多語 |
