# CivicFlow｜懂你通

數位平權 × 友善共融｜2026 臺北秋季程式設計節冠軍提案規劃

核心主張：不是讓人適應政府服務，而是讓政府服務適應每個人。

文件版本：2026 年 11 月 7 日｜提案與開發規劃稿

## 一、執行摘要

CivicFlow 是以城市通微服務為基礎的自適應市政理解平台。以同一套服務資料，依使用者自主選擇的語言、閱讀難度、圖像需求與操作步調，轉換成可理解、可完成的任務流程。三類主要服務對象為外籍人士、兒童與數位素養不足者，但不以身分標籤推斷能力。

建議 MVP：以臺北市立圖書館借閱證申辦為主情境，公共廁所設施查詢為第二情境，證明同一理解引擎可跨市政服務重複使用。

## 二、競賽策略與限制

| 階段 | 評分重點 | 策略 |
| --- | --- | --- |
| 初選（約 2 分鐘） | 服務應用 40／視覺呈現 30／技術完整度 30 | 優先呈現一條順暢、令人秒懂的任務流程 |
| 決選（約 5 分鐘） | 服務應用 25／服務完整度 30／技術穩定度 20／視覺 15／創意公益性 10 | 展示資料可信、可整合、可維運、跨情境能力 |

- 僅能投影作品實際運作畫面，禁止簡報。

- 核心及關鍵資料需使用公開合法的開放資料，並註明來源。

- 軟體與套件須符合開源及授權規定；成果依競賽規定採 AGPL。

- 正式作品執行時若有 LLM 即時推論，須完全在裝置端；不能使用雲端或遠端 LLM 推論。

- 賽前可準備範圍、提交期限及現場規則仍須向主辦核對。

## 三、情境比較與選題

| 方案 | 優勢 | 風險／取捨 |
| --- | --- | --- |
| 城市生活任務導航 | 跨族群、跨服務、適合擴充 | 需聚焦具體任務，避免變成普通搜尋 |
| 圖書館借閱證引導（主推） | 資格分支清楚、易於演示三種模式 | 申辦規則須人工核對、更新 |
| 公共廁所查詢（第二場景） | 可用地點與設施欄位、容易完成 | 單獨呈現差異化較弱 |
| 防災避難易懂通 | 公益性強、展示張力大 | 不可混淆避難地點與即時開設狀態 |
| 市政申辦助手 | 高度切題 | 行政規則複雜，短期不宜做太廣 |
| 交通理解助手 | 使用族群廣 | 即時路線與票價維護複雜 |

選題原則：一個引擎、兩個情境、三種使用方式。先做深度，再做廣度。

## 四、產品功能設計

### 多語 × 理解層級

繁中、英文、越南文；語言與閱讀難度分離，不將外籍人士等同低識字者。

### 逐步任務引導

一次顯示一個動作，使用者知道目前進度、下一步及完成條件。

### 圖像化與易讀模式

大圖示、簡短語句、可選大按鈕及較低資訊密度。

### 理解確認與替代解釋

在關鍵步驟詢問是否理解；需要幫助時提供更簡短的解釋、例子或原文。

### 條件式資格與文件引導

依申辦者身分與年齡等已明確輸入的條件決定流程，不交由 LLM 自行判定官方規則。

### 來源可追溯

每一條資格、文件與步驟附官方來源、更新時間與版本。

### 跨情境複用

圖書館申辦與公共廁所查詢共用理解偏好、任務元件與操作規則。

## 五、三種代表性使用者 Demo

| 使用者 | 操作 | 展示重點 |
| --- | --- | --- |
| 越南籍居民 | 選越南語→借閱證→查看適用證件→找到館舍 | 語言轉換與行政資訊理解 |
| 11 歲兒童 | 圖像模式→年齡條件分支→準備文件 | 分齡內容與圖卡引導 |
| 不熟悉手機的成年人 | 大按鈕→一步一題→點選「我不懂」 | 低操作負擔、替代解釋 |

注意：三者是示範情境，不應自動把某一種身分對應某種能力。

## 七、技術架構

官方資料 CSV／API／人工核對規則 → 結構化 Service Schema → 流程規則引擎 + 理解呈現引擎 → Vue 3 自適應 UI → 任務完成與理解回饋。

| 層級 | 建議技術 | 目的 |
| --- | --- | --- |
| 前端 | Vue 3 + TypeScript + Vite | 符合城市通微服務方向 |
| UI | Tailwind CSS | 建立一致的圖像化及自適應元件 |
| 狀態 | Pinia | 儲存偏好、流程進度 |
| 多語 | Vue I18n／版本化 JSON | 可審核的固定翻譯 |
| 規則 | TypeScript + JSON Schema | 可解釋的資格分支 |
| 資料 | 官方 CSV + 本地 JSON | 易部署、可離線展示 |
| 地圖 | Leaflet + 合規圖資 | 開源地圖顯示 |
| 測試 | Vitest + Playwright | 分支與端到端流程驗證 |

## 八、核心資料模型

每個服務步驟至少包含：service_id、step_id、action、condition、各語言與閱讀層級 content、icon、source_id、requires_confirmation。

嚴格區分 Fact（官方事實）、Presentation（呈現方式）、Interaction（引導與確認）。只允許呈現層依偏好改變，不可任意更動官方資格條件。

## 九、自適應機制與測量

先由使用者自主選擇偏好；若點選「我不懂」，優先提供替代文字、圖示或實例；必要時顯示官方原文。避免未經同意推測個人能力。黑客松階段建議規則式引擎，不必投入強化學習模型訓練。

- Task Completion Rate：任務正確完成比例。

- Time to Completion：完成時間。

- Comprehension Accuracy：對資格、文件、下一步的理解正確率。

- Assistance Rate：需要額外協助的頻率。

可用少量志願者進行探索性可用性測試，記錄樣本數、任務與限制；不能將小樣本改善幅度宣稱為普遍有效。

## 十一、團隊分工與開發節奏

| 角色 | 任務 |
| --- | --- |
| 產品／發表 | 鎖定情境、流程、資料驗證、Demo 劇本 |
| UI/UX | 三種理解模式、圖卡、無障礙互動 |
| 前端 | Vue 3 頁面、狀態管理、元件 |
| 資料／後端 | 官方 CSV、規則 JSON、來源管理 |
| 整合／測試 | 整合、斷網測試、授權、部署與演示 |

- 前 2 小時：鎖定場景、規則來源與操作腳本。

- 第 3–8 小時：完成主要流程與畫面。

- 第 9–14 小時：多語、圖像與理解確認。

- 第 15–19 小時：第二場景、測試、來源及授權檢查。

- 最後階段：凍結功能、測試重啟與投影、練習發表。

## 十三、落地與評審問答

| 可能質疑 | 回答策略 |
| --- | --- |
| 與翻譯工具有何不同？ | 我們轉換的是可執行的服務流程，不只文字。 |
| AI 會不會編造規則？ | 資格由經核對的結構化規則決定，呈現層不能改寫事實。 |
| 為何要自適應？ | 語言、閱讀密度、圖像及操作步調是獨立需求。 |
| 如何整合？ | 採城市通 Vue 3 微服務方向與可重用 Schema。 |
| 如何證明有效？ | 以完成率、理解正確率、時間與協助次數測試。 |
| 如何維運？ | 資料與呈現分離，保留版本、來源與更新檢查。 |
| 隱私如何處理？ | 偏好優先本機保存，避免收集不必要的個資。 |

## 十四、最終結論

首選方案：CivicFlow 懂你通；主情境為圖書館借閱證引導，第二情境為親子與無障礙公廁查詢。核心差異化在於一個自適應理解引擎跨族群、跨服務複用。

最重要的取捨：先完成圖書館完整流程、三種呈現模式、官方來源驗證；其餘 AI 功能僅在時間與合規條件允許時增加。

最終口號：「同一座城市，不同的理解方式，一樣的使用權利。」
