# Taipei Maze｜北車不迷路

> **2026-11-07 架構更正：** 依使用者提供的《2026 城市通入門指引》，正式作品為城市通 Flutter App 的 **WebView 微服務網頁**，前端語言、框架不限；本案採 HTML／CSS／TypeScript 網頁，透過 `flutterObject` 呼叫宿主掃碼。本文早期獨立 Flutter 導航客戶端、Dart 引擎及 just_audio 範例保留為提案歷程，已由新版 [SPEC](./SPEC.md) 與[城市通開發指南](./城市通開發指南.md)覆寫，不再作實作指示。七語（中英越印尼泰韓日）、預生成音檔、無障礙硬限制及禁止中國相關資源要求保留。原創程式碼採 AGPL-3.0-or-later；TownPass 上游 GPL 與第三方權利各自保留。

> **2026 Codefest｜數位平權 × 友善共融**  
> 核心議題：看不懂（理解限制）

## 一、問題與願景

臺北車站具有多樓層、多系統轉乘、地下街與大量出口。現有指示牌及平面地圖雖提供資訊，仍要求使用者自行判斷位置、理解樓層及規劃路線，對外籍人士、兒童、數位素養不足者尤其不友善。

**核心主張：我們不只幫使用者找到最短的路，而是找到他真正看得懂、走得到的路。**

## 二、解決方案

在車站既有告示牌旁規劃 QR Code 定位點。使用者掃描後即可知道所在位置與樓層，選擇目的地，取得圖像化、逐步的導航指引；沿途可再次掃碼確認位置並重新規劃。

### 主要功能

1. **掃碼定位**：每個 QR Code 綁定固定節點，顯示所在樓層與附近地標，不依賴室內 GPS。
2. **目的地導航**：支援出口、轉乘入口、百貨、地下街等目的地；出口可連結具體地標。
3. **跨樓層地圖**：路線隨樓層切換，清楚顯示電梯、樓梯與電扶梯。
4. **沿途重新定位**：掃描下一個 QR Code 確認是否走在正確路線上；必要時重算路線。
5. **一鍵尋找設施**：廁所、無障礙廁所、電梯、售票機、電子票證加值、行動充電、進站閘門等。
6. **個人化路徑**：最短路徑、少轉彎、無障礙、避開樓梯、優先電梯等。
7. **自適應介面**：多語、大字、高對比／易讀模式、圖像指示、一次只呈現下一步。
8. **多語語音導航（TTS）**：將逐步指引轉為使用者選擇語言的語音，支援重播、語速調整與掃碼重新定位後更新播報。
9. **進階構想**：360 度環景與地標對照（非 MVP 必要功能）。

## 三、差異化

| 面向 | 傳統告示牌／平面圖 | Taipei Maze |
|---|---|---|
| 定位 | 使用者自行找「你在這裡」 | 掃 QR Code 確認所在節點 |
| 指引 | 同時閱讀整張地圖 | 逐步顯示下一個動作 |
| 樓層 | 自行理解樓層關係 | 路線與樓層同步切換 |
| 無障礙 | 需要自行判斷路線 | 依通行條件排除不可走的邊 |
| 迷路後 | 回頭找地圖 | 沿途再次掃碼重新定位 |
| 出口 | 出口編號 | 出口綁定目的地與地標 |
| 語音 | 多仰賴閱讀文字標示 | 多語 TTS 播報下一步、可重播與調整語速 |

**關鍵創新：最容易理解的路線，不一定是最短的路線。**

## 四、三類使用者的自適應體驗

| 使用者 | 主要障礙 | 建議呈現 |
|---|---|---|
| 外籍人士 | 不熟悉中文標示、出口與地標 | 多語文字與 TTS、圖像、地標名稱對照 |
| 兒童 | 難以理解複雜地圖與方向 | 大圖示、短句、語音提示、少轉彎、一步一指令 |
| 數位素養不足者 | 操作步驟與資訊量過多 | 大按鈕、易讀文字、慢速語音與重播、少選項、掃碼快速重新定位 |

使用者可自行選擇語言、字體大小、圖像化程度及路徑需求；不應僅依年齡或身分推斷能力。

## 五、路徑規劃與技術架構

### 室內路網

以圖論建模：

- **節點（Node）**：走道交會點、QR 定位點、出口、設施、樓層連接點。
- **邊（Edge）**：可通行走道、樓梯、電梯、電扶梯，記錄距離、方向、樓層、可及性與理解複雜度。
- **演算法**：Dijkstra 或 A*，依使用者偏好調整成本。

示意成本函數：

$$
C(P)=\sum_{e\in P}(\alpha d_e+\beta t_e+\gamma c_e)
$$

其中 $d_e$ 為距離、$t_e$ 為預估通行時間、$c_e$ 為路線理解複雜度（如轉彎、換樓層或地標不明確）；權重由模式決定。**無障礙限制應作為硬性可行性條件，不可僅以較高成本取代。**

### 建議架構

```text
Flutter App（導航與本地音檔播放）／城市通微服務整合層（依官方交付要求）
  ├── QR Code Scanner → 定位節點
  ├── 使用者偏好／自適應 UI
  ├── 多樓層地圖渲染
  ├── 圖論路徑規劃引擎
  ├── 設施查詢與路線指引
  ├── 固定句子 ID / 多語文字資源 / 預生成音檔播放器
  └── 本地路網 JSON / 官方開放資料
```

導航客戶端依團隊最新決策採用 Flutter，路網與語音資源放在本地 assets；以 CustomPainter／SVG 顯示分層地圖。**注意：競賽城市通微服務交付格式若要求 Vue 3 / Vite，應另外製作相容的 Web 微服務入口或確認 Flutter Web 是否被接受，不可假設 Flutter App 自動符合交付規範。**核心導航不依賴 LLM。

### 多語語音導航：固定中文句子庫 → 批次翻譯 → 預生成 TTS → Flutter 本地播放（確定採用）

**架構決策**：開發階段先建立固定繁體中文句子／片語庫，批次翻譯成目標語言，人工校對，再以 TTS 批次生成音檔。將文字及音檔一同打包進 Flutter assets；**使用者導航時只查詢句子 ID 並播放現成音檔，不做即時翻譯、即時 TTS 或 LLM 推論，也不依賴網路 API。**

```text
固定繁體中文句子庫（ID + 中文原文 + 情境）
  → 開發階段批次翻譯（英文／日文／韓文／越南文／印尼文／泰文）
  → 人工校對語意、方向、樓層與發音
  → 開發階段批次 TTS 產生音檔
  → 音檔品質檢查、格式轉換、建立 manifest
  → Flutter assets/audio/{language}/{sentence_id}.mp3
  → 導航事件觸發本地播放（完全不需即時推論）
```

#### 固定句子庫（首批示例）

| ID | 繁體中文 | 觸發時機 |
|---|---|---|
| `nav_start` | 導航開始，請依照指示前進。 | 開始導航 |
| `go_straight` | 請直走。 | 直行 |
| `turn_left` | 請左轉。 | 左轉 |
| `turn_right` | 請右轉。 | 右轉 |
| `take_elevator` | 請搭乘電梯。 | 電梯節點 |
| `go_upstairs` | 請上樓。 | 上樓 |
| `go_downstairs` | 請下樓。 | 下樓 |
| `scan_qr` | 請掃描附近的 QR Code，確認目前位置。 | 定位確認 |
| `route_updated` | 已為您重新規劃路線。 | 路線更新 |
| `destination_arrived` | 您已抵達目的地。 | 抵達 |
| `find_restroom` | 正在為您尋找最近的廁所。 | 設施搜尋 |
| `accessible_route` | 已切換為無障礙路線。 | 模式切換 |

目標可擴充至 **30–50 個固定句子或片語 × 7 種語言（含繁中）＝約 210–350 個音檔**。MVP 可先完整驗證繁中、英文及至少一種外籍居民常用語言，再視時間擴充；「支援」必須以已產生且測試通過的音檔為準。

#### 動態導航資訊的處理

「請直走 30 公尺後右轉」可以使用固定片語與距離音檔組合，例如 `go_straight` + `distance_30m` + `then_turn_right`。**不同語言的語序、連音與文法不一定能直接拼接**，因此每種語言應有自己的組合模板。對容易不自然的情境，優先預生成完整常用句；距離可採 10、20、30、50 公尺等有限級距，並避免聲稱未經測量的精確距離。

#### Flutter 本地播放範例

```dart
import 'package:just_audio/just_audio.dart';

class NavigationVoiceService {
  final AudioPlayer _player = AudioPlayer();
  String language = 'zh-TW';

  Future<void> speak(String sentenceId) async {
    final path = 'assets/audio/$language/$sentenceId.mp3';
    await _player.stop(); // 新導航事件先停止舊語音
    await _player.setAsset(path);
    await _player.play();
  }

  Future<void> dispose() => _player.dispose();
}
```

此為最小示意；正式實作需在 `pubspec.yaml` 宣告 assets、處理缺檔回退、播放佇列／中斷策略、語速控制、重複觸發去抖、靜音與音量、不同平台的音訊行為。語音與畫面應共用同一個 `instruction_id`，避免播報與路線不一致。

#### 語音品質與授權

- 固定文字先由人工核對；翻譯不可改變左右方向、樓層、出口或安全提示。
- 開發階段可批次製作音檔，但須確認所選 TTS 工具／模型、生成音檔的商用與再散布授權，符合競賽開源及成果交付規範；不可假設所有線上 TTS 產物都能自由散布。
- 逐一檢查語速、停頓、數字／樓層發音及不同語言的自然程度。
- 介面提供播放／暫停、重播、語速、靜音；文字與圖像始終保留，不讓語音成為唯一資訊來源。
- 透過本地 assets 可離線播放，亦避免競賽現場網路不穩及執行期遠端 AI 推論限制。

## 九、決選展示重點

1. **真實場域**：清楚標示示範範圍，展示已核對的節點與設施。
2. **完整情境**：從掃碼、選終點、規劃、換樓層到抵達。
3. **自適應差異**：同一條路在不同理解需求下顯示不同指引，並以所選語言播放 TTS。
4. **技術可信**：展示路網資料結構、演算法與無障礙硬限制。
5. **落地計畫**：QR 部署、場站合作、維護及資料更新機制。

## 十三、最新決策與開發注意事項（2026-11-07）

1. **導航客戶端採 Flutter**；需另外確認城市通微服務的正式交付相容性。
2. **語音採預生成音檔**，不是在使用者手機上即時呼叫 TTS，也不是雲端語音 API。
3. **翻譯及 TTS 只發生在開發／建置階段**；上線後由 `language + sentence_id` 讀取對應音檔。
4. **語音是多模態引導的一部分**：箭頭、圖像、文字、樓層地圖與語音須同步。
5. **先做可靠路網與完整導航，再擴充語言數**；語音功能不能犧牲路徑正確性與無障礙安全性。
6. **既有告示牌加 QR Code 為部署構想**，正式場站設置須取得管理單位同意；競賽可使用模擬 QR 標示。

### 賽事資料備註

## 十四、24 小時可完成、可實際 Demo 的 MVP 開發計畫（2026-11-07 更新）

### 14.1 核心交付目標與範圍

**唯一主線：掃描 QR Code → 確認起點 → 選擇目的地 → 規劃跨樓層路線 → 圖像化與多語語音指引 → 中途重新掃碼 → 抵達。**

| 項目 | 24 小時目標 | 限制／驗收 |
|---|---|---|
| 地圖 | B1、B2 各一個連續局部區域 | 僅宣稱經核對的示範範圍，不假裝覆蓋整個北車 |
| Graph | 20–30 個節點 | 走道交會、轉角、電梯、樓梯、出口及設施節點 |
| QR Code | 4–6 個定位點 | 實體印出的 QR 可被手機相機掃描 |
| 目的地 | 4–6 個 | 至少含出口、廁所及電梯 |
| 路徑模式 | 一般最短路線、無障礙路線 | 無障礙模式以硬性條件排除樓梯等不可通行邊 |
| 地圖展示 | 兩層底圖與路線疊圖 | 樓層切換後仍保留路線狀態 |
| 導航指引 | 大箭頭、一步一題、地標與樓層提示 | 文字、圖示與語音對應同一導航事件 |
| 多語 | 繁中、英文、越南文 | 固定句子庫，預先翻譯校對並產生音檔 |
| 自適應 | 標準／易讀大字模式 | 可自行切換，不以年齡直接推測能力 |
| 離線 | 路網、地圖與音檔本地打包 | 不依賴即時 LLM、翻譯 API 或 TTS API |

**P0（必做）：** QR 掃描、局部地圖、Dijkstra、跨樓層、無障礙限制、目的地、圖像指引、三語離線播報、兩種介面模式。

**明確不做：** 完整北車路網、360 度環景、GPS／藍牙／Wi-Fi 室內定位、即時 AI 翻譯、即時 TTS、動態障礙物辨識、完整路網標註器。

## 十六、ML 擴充：預測路線理解難度（Cognitive-Aware Route Ranking）

### 16.1 問題與產品價值

傳統室內導航主要尋找最短距離或最短時間，但在北車這類多樓層、岔路密集的空間，**最短路線不一定最容易理解**。Taipei Maze 希望在「路線確實可通行」的前提下，從多條候選路線中推薦較少轉彎、較少複雜岔路、具有清楚地標的路線。

此功能對應競賽主題「看不懂（理解限制）」，也能在初選展示「最短」與「易懂」路線的差異；但不得將未經驗證的模型預測描述成已證實能降低迷路率。

### 16.2 安全優先的兩階段規劃

1. **硬性限制先行：** 在 Graph 中先排除無法通行的邊，例如輪椅模式下的樓梯、不允許逆行的電扶梯、受限付費區或已知封閉通道。不可僅以較高權重取代硬性禁止。
2. **候選路線生成：** 使用 Dijkstra / A* 及 K-shortest paths（例如 Yen's algorithm）產生 2–5 條有效、合理且不過度繞路的候選路線。
3. **理解難度評分：** 先使用規則基線；有足夠資料時以 ML 預測候選路線的理解難度。
4. **路線排序：** 綜合距離、時間、理解難度，讓使用者選擇「最快」或「容易理解」。模型只負責排序，不得創造不存在的通道。
5. **結果可解釋：** 顯示「少 2 次轉彎」「經過明顯電梯標誌」等可直接由路網資料驗證的理由，而不是無依據的 AI 宣稱。

### 16.3 特徵工程（Feature Engineering）

| 特徵 | 欄位名稱 | 取得方式 | 預期作用 |
|---|---|---|---|
| 路線總長 | `distance_m` | 已校準路網邊長總和 | 反映行走負擔 |
| 轉彎次數 | `turn_count` | 連續邊夾角與轉彎門檻 | 轉彎越多，指令越複雜 |
| 複雜岔路數 | `complex_junction_count` | 節點分支數與轉向選項 | 降低選錯方向的機會 |
| 跨樓層次數 | `floor_change_count` | 電梯／樓梯／電扶梯邊 | 反映跨樓層理解成本 |
| 導航步驟數 | `instruction_count` | 指令生成器輸出 | 反映需記住的步驟 |
| 明確地標數 | `landmark_count` | 人工驗證的地標與節點關聯 | 有助於確認方向 |
| 相似走廊數 | `ambiguous_segment_count` | 人工標記易混淆路段 | 反映辨識難度 |
| 轉乘或閘門數 | `gate_transfer_count` | Graph 邊與節點類型 | 反映通行與認知負擔 |

注意：`distance_m` 必須有可靠的比例尺或實測資料；若只有 PDF 像素，應標示為相對距離，不可直接當作公尺。特徵的方向與重要性需要實測，不能先假設其因果關係。

### 16.4 無資料時的 MVP 基線：可解釋的規則模型

先用標準化特徵建立認知成本，例如：

\[
R(P)=w_1\,\mathrm{turns}(P)+w_2\,\mathrm{junctions}(P)+w_3\,\mathrm{floorChanges}(P)+w_4\,\mathrm{ambiguous}(P)-w_5\,\mathrm{landmarks}(P)
\]

\[
C(P)=lpha\,\widehat{D}(P)+eta\,\widehat{T}(P)+\gamma\,\widehat{R}(P)
\]

其中帽號代表經適當尺度正規化的數值；權重為**示範用可調參數**，不是已訓練或驗證的 ML 模型。應限制最大繞路幅度，避免「易懂」模式推薦不合理的遠路。若未完成驗證，預設仍提供最短可行路線。

### 16.5 有標註資料後的真正 ML 版本

**訓練目標：** 預測使用者對一條路線的理解難度，或學習兩條路線哪一條更容易完成。

- **資料收集：** 讓受測者依照不同路線完成相同或相近的尋路任務；記錄完成時間、走錯次數、求助次數、是否抵達，以及 1–5 分的主觀理解難度。
- **標籤定義：** 可先以主觀難度分數做回歸；也可用同一受測者對兩條路線的偏好做 pairwise ranking。必須說明測試條件與樣本數。
- **模型候選：** Linear Regression / Ridge 作為可解釋基線；Random Forest / Gradient Boosting 作為非線性模型；小型 MLP 僅在資料量足夠時嘗試。
- **避免資料洩漏：** 以受測者或路線／場景分組切分訓練與測試集，避免同一條路線的近似樣本同時出現在兩邊。
- **評估指標：** MAE（難度回歸）、Spearman rank correlation（排序一致性）、pairwise accuracy（路線偏好）；產品端另追蹤任務成功率、走錯次數與完成時間。
- **模型部署：** 可離線預先計算每條候選路線的評分，存入 JSON；若需手機端即時推論，優先使用小模型及可在 Flutter 本地執行的推論方式。**不呼叫 API，不依賴任何 LLM。**

**重要限制：** 若訓練標籤只是人工規則公式的輸出，模型只是模仿規則，不能聲稱已學到真實人類理解難度。少量使用者測試只能提供初步證據，不代表普遍有效。

### 16.6 建議資料格式與程式介面

```json
{
  "route_id": "candidate_02",
  "valid": true,
  "features": {
    "distance_m": 120,
    "turn_count": 2,
    "complex_junction_count": 1,
    "floor_change_count": 1,
    "instruction_count": 5,
    "landmark_count": 3,
    "ambiguous_segment_count": 0,
    "gate_transfer_count": 0
  },
  "cognitive_score": 0.31,
  "score_source": "rule_baseline_v1"
}
```

以上數值僅為資料結構示例，不代表北車真實路線測量結果。`score_source` 應區分 `rule_baseline_v1` 與未來的 `ml_model_v1`，避免誤稱規則為 ML。

```text
QR 定位 + 目的地 + 無障礙條件
       ↓
Graph 硬性限制與有效性檢查
       ↓
候選路線（最短、替代路線）
       ↓
特徵萃取 → Rule Baseline / Offline ML Ranker
       ↓
「最快」與「容易理解」路線比較
       ↓
Flutter 圖像導航 + 本地多語 MP3
```

### 16.7 24 小時黑客松的實作順序與停損

| 時間／條件 | 工作 | 完成標準 |
|---|---|---|
| 核心導航完成後，預留約 1–2 小時 | 計算轉彎、岔路、換樓層與地標特徵 | 至少 2 條候選路線可產生特徵 JSON |
| 再預留約 1 小時 | 加入規則式認知成本與路線切換 UI | 「最短／易懂」可切換，並顯示可核對的差異 |
| 若已有真實標註資料且 Demo 穩定 | 離線訓練簡單 ML 模型並輸出分數 | 能展示測試結果、模型來源與基線比較 |
| 若時間不足或缺乏標註資料 | 停在規則式版本 | 不犧牲 QR、跨樓層、無障礙及語音閉環 |

### 16.8 對應競賽評分與展示方式

- **初選服務應用（40%）：** 展示「最短不一定最好懂」，直接對應理解限制與友善共融。
- **初選視覺呈現（30%）：** 同畫面比較兩條路線，標示距離、轉彎數與清楚地標；不要用無法解釋的單一 AI 分數代替資訊。
- **初選技術完整度（30%）：** 說明 Graph、候選路線、特徵工程、評分與資料來源的清楚分工。
- **決選技術完整度（30%）：** 若有真實 ML 模型，展示訓練／驗證方式及離線部署；若沒有，誠實說明目前是規則基線。
- **決選技術穩定度（20%）：** 模型失敗或資料不足時自動回退最短可行路線；無障礙限制始終優先。
- **決選創意及公益性（10%）：** 強調從「最短路徑」轉向「理解友善路徑」，並公開可重現的資料格式與評估方法。

**最終決策：** 將 Cognitive-Aware Route Ranking 列為 **P1 高價值擴充**。24 小時內優先完成可解釋的規則版與雙路線比較；只有取得可靠標註與完成測試時，才將其稱為真正的 ML 預測功能。

### 17.5 技術完整度與落地可行性的答辯要點

1. **資料來源：** 官方站圖及設施資料只提供參考；可導航的 Graph 需自行標註、核對路口與跨樓層連接。
2. **安全限制：** 無障礙是硬性可通行約束，不可僅靠 ML 的加權分數；付費區、單向通道、電扶梯方向也須標記。
3. **定位誠實性：** QR 掃碼只能確認掃碼當下的位置，不能宣稱連續即時定位；重新定位依靠再次掃碼。
4. **離線：** 路網、語音、文字、圖片與可選的 ML 模型都封裝於裝置，不呼叫外部 API。
5. **部署：** 實際站內 QR 設置需管理單位許可；競賽現場使用模擬標牌；正式服務需現場勘查、無障礙驗證與維護機制。
6. **競賽交付形式：** 若規則要求特定 Web 微服務／TownPass 整合，必須先確認 Flutter 是否符合規範，必要時改採 Vue Web 版本。
7. **開源：** 程式碼、資料格式與自製素材可開源；官方地圖、第三方模型、音檔與套件須逐一核對重製及再散布授權。
