# Taipei Maze｜Wi-Fi 樓層辨識 PoC 技術評估與試作指南

日期：2026-11-07｜版本：討論稿 0.1｜狀態：研究與試作提案，尚未實作、量測或納入正式交付

> **建議方向：值得做小型 PoC。先以 Android／量測資料驗證 Wi-Fi 樓層分類，再將穩定結果用於自動切換地圖；QR 保留作明確節點確認與恢復。是否進一步自動確認換層，另以實測決定。**

本文整理使用者、學長構想與討論中的技術判斷，供負責研究及實作的組員分析。新增文件已獲授權；不代表已授權安裝依賴、蒐集定位資料、修改宿主、部署，或認定所有工程建議已定案。本文不覆寫 [SPEC](./SPEC.md)，不將此實驗自動加入 P0／P1，也不宣稱官方要求使用 Wi-Fi 定位。

## 1. 構想來源與目標

學長曾嘗試利用室內多個 Wi-Fi 訊號的差異判斷位置。使用者進一步確認：可利用多個 Wi-Fi 各自的訊號強度，以及某些 Wi-Fi 是否能偵測／連接，推測所在區域或樓層。

本專案關注的應用是：使用者換樓層後，系統自動辨識並切換地圖，減少反覆按「我已上樓／下樓」的負擔。只辨識有限樓層，能把研究範圍收斂；「不同樓層一定容易且明確可分」仍是待驗證假設。

**目前未知：** 學長的原始碼、資料格式、可重用權利、當年裝置／OS、現場 AP 配置、測試方法及實際成績。不能從經驗描述推論現在的 Android／iOS 一定支援，或北車會有同樣效果。

## 2. 結論與功能分級

| 層次 | 可以嘗試的成果 | 成立條件與界線 |
| --- | --- | --- |
| 演算法 PoC | 從 RSSI 指紋預測資料場域的樓層 | 有標註資料、獨立測試與不確定狀態 |
| Android 取樣 PoC | 原生取得周遭 AP 與新鮮 RSSI | 真機、權限、掃描限制與生命週期處理 |
| 輔助切圖 | 穩定辨識換層後切換檢視地圖 | 來源／時間清楚，保留手動及 QR 備援 |
| 自動確認到層 | 在受控情境中推進特定跨層步驟 | 額外驗證與 SPEC／狀態契約調整，第一階段不啟用 |
| 精確室內定位 | 持續知道樓層內 x/y 或特定設備落點 | 本提案不承諾，不能由樓層分類成功推得 |
| iOS 同等 Wi-Fi 掃描 | 用相同掃描法支援 iPhone | 現有公開 API 有根本限制，不列為本 PoC 必成條件 |

技術挑戰適合投入探索，但應把「資料是否可取得」「模型是否有效」「導航是否可採用」分開驗證。分類器的計算不一定是最耗時部分；資料蒐集、平台能力及誤判控制可能更費工。

## 3. 方法原理：Wi-Fi fingerprinting

### 3.1 一次訊號指紋

將同一次掃描中可見的 AP 身分、RSSI、頻段及觀測時間組成特徵，和已標註樓層的樣本比較。輸出目標先限定為 `floor_id` 或 `unknown`，不先估計精確座標。

| 特徵 | 用途 | 注意事項 |
| --- | --- | --- |
| 可見 AP 集合 | 哪些訊號經常在某樓層出現 | 「沒看到」不等於永久不存在 |
| 每個 AP 的 RSSI | 比較多個訊號的強弱組合 | 不直接當精確距離 |
| AP 缺失標記 | 區分未偵測與已量測弱訊號 | 不把缺失填成真實 0 dBm |
| 頻率／頻段 | 區分訊號特性及資料配置 | 不直接當樓層標籤 |
| 觀測時間、scan ID | 排除過期或重複資料 | 收到 callback 的時間不等於 RF 觀測時間 |

Wi-Fi 名稱為 SSID，AP 位址可由 BSSID 表示。應辨識不同 AP，而非只靠可能重複的名稱；也不要假設一個 BSSID 永遠等同一台固定實體設備。Android `ScanResult` 提供 BSSID、RSSI `level` 與自開機起算的觀測 `timestamp`。[Android ScanResult 官方文件](https://developer.android.com/reference/android/net/wifi/ScanResult)

### 3.2 可見性與連線成功率不同

第一版優先使用「掃描可見 AP＋RSSI」，通常不需要逐一連線或登入公共網路。連線失敗也可能涉及認證、容量、連線策略等因素，不能直接解讀為不在該層；反覆切網路還可能干擾既有服務。

公家機關提供 Wi-Fi 不等於公開其逐樓層指紋。熱點名稱、地址或 AP 清單通常不足以直接訓練本場域模型，仍需要「在已知位置量到什麼訊號」的資料。

## 4. 平台與權限：先驗證能拿到什麼

### 4.1 Android：可試，但不能假設高頻即時

官方掃描文件要求依 OS／target 處理 `ACCESS_FINE_LOCATION`、Wi-Fi 權限及定位服務；Android 9 起前景主動掃描上限為兩分鐘四次，Android 10 以上沿用。掃描失敗時可能讀到舊結果。[Wi-Fi scanning overview](https://developer.android.com/develop/connectivity/wifi/wifi-scan)

Android 13 的 `NEARBY_WIFI_DEVICES` 不全面取代定位權限；`startScan()`／`getScanResults()` 仍有其要求。本功能實際用訊號推導位置，不能宣告不作定位來規避權限。[Wi-Fi permissions](https://developer.android.com/develop/connectivity/wifi/wifi-permissions)

工程上要驗證：

- 真機及目前 target SDK 下的 manifest、runtime 權限與拒絕恢復。
- 主動掃描的成功率、節流、平台被動掃描事件及實際觀測間隔。被動事件不是可要求每秒更新的保證。
- `EXTRA_RESULTS_UPDATED`、AP observation timestamp 及新舊批次；讀到 cached results 時不可增加「連續穩定命中」次數。
- 每個 AP 的資料新鮮度；同一批清單內的 AP 也可能有不同最後觀測時間。
- 背景、螢幕鎖定、原生相機覆蓋、返回頁面後是否仍有合法且新鮮的資料。
- 能耗與掃描對服務的影響。

兩分鐘四次不等於每三十秒一定有一次成功掃描，也不保證換層後能立即更新。開發者選項關閉節流可用於局部除錯，但成績必須另記；不可拿它當一般使用者環境的即時能力。

Wi-Fi 定位需要定位相關權限，不表示要以 GPS 座標導航。這是相對現有 QR 主流程新增的選配權限，需先討論產品文案及 SPEC，不應讓拒絕者失去 QR 導航。

### 4.2 iOS：不可假設 Flutter plugin 能解決

Apple 表示 iOS 沒有通用 Wi-Fi 掃描 API，`NEHotspotHelper` 需要特殊 entitlement，且不適合作一般 Wi-Fi 定位。讀目前連線資訊，也不等於取得周遭多 AP 指紋。[Apple TN3111](https://developer.apple.com/documentation/technotes/tn3111-ios-wifi-api-overview)

第一版建議 Android 限定；iOS 回傳 unsupported，沿用 QR／手動流程。不以 private API、特殊測試權限或換套件名稱假稱支援一般使用者。Core Location 也不能先假設在北車提供本案所需且可驗證的樓層與精確 anchor。

### 4.3 Vue／WebView：需要原生 adapter

一般網頁的 Network Information API 描述目前連線類型及品質，不提供周遭 Wi-Fi BSSID／RSSI 清單。[Network Information API 規格](https://wicg.github.io/netinfo/)

建議資料流為「Android 原生掃描 → Flutter adapter／handler → Web 分類器與決策器 → 地圖」。若改由 Native 完成分類，也需相同模型版本與測試契約。既有 TownPass `location` handler 不是 Wi-Fi 指紋或樓層辨識能力，不應直接拿其回覆充當本案樓層。

## 5. 資料取得路線

### 5.1 優先順序

1. 確認學長是否有可使用的原始量測、標註、程式與裝置記錄；舊場域資料只驗證舊場域，不自動適用北車。
2. 若可安排授權場域與人員，做少量真機跨層量測，驗證取樣及切層行為。
3. 目前只能遠端作業時，先用公開真實指紋資料做分類，Android 取樣能力另行驗證。
4. 合成資料用於程式、狀態與異常測試；不作北車定位準確度證據。

### 5.2 可評估的公開資料：UJIIndoorLoc

UJIIndoorLoc 來自西班牙 Universitat Jaume I，多棟、多樓層資料包含 520 個 AP 強度欄位及樓層標籤，並提供訓練／驗證檔。該資料以 `100` 表示 AP 未偵測到，不能當成真實 RSSI。UCI 頁面列為 CC BY 4.0。[UCI 官方資料頁](https://archive.ics.uci.edu/dataset/310/ujiindoorloc)

此為候選來源，尚未下載、訓練或納入正式包。使用前依 repo 規範核對來源、權利及所採檔案，記錄版本、hash、顯名與審查；本文件的連結不代表完成整體來源核准。

資料中的其他特徵，例如 BuildingID、Floor、使用者、裝置及時間，需明確區分標籤、分組資訊與可用輸入。不得讓模型讀取正確樓層再展示為預測。第一版可先限定一棟建築，避免把建築分類成功掩蓋樓層失敗。

資料場域與北車 AP 身分、配置不同，模型不能直接移植為北車模型。公開資料若沒有連續跨層真實軌跡，不能靠自行拼接樣本就聲稱測得實際換層延遲。

### 5.3 建議量測紀錄

| 欄位 | 用途 |
| --- | --- |
| `capture_session_id`、`scan_id` | 區分量測批次與去重 |
| `site_id`、`building_id` | 明確場域；樓層 ID 不能跨建築混用 |
| `device_code`、OS／target／設定 | 匿名裝置代碼，追查裝置差異及是否改節流 |
| `observed_at`／原生單調時間 | 量測時間與資料新鮮度；保留時間基準說明 |
| AP ID、`rssi_dbm`、頻率、last seen | 指紋與原始品質資訊 |
| `true_floor`、區域／參考點 | 由量測者核對的真值，不能用模型預測回填 |
| `trajectory_id`、換層方式 | 同一行走軌跡與電梯／樓梯等條件 |
| ground-truth 換層標記 | 計算時間延遲，註明標註方式與誤差 |
| 來源、權利與核對狀態 | 是否可供訓練、展示、公開及移交 |

樓層上應包含不同水平區域、方向、設備出入口及停留點；重複量同一角落不能代表全層。若測試電梯或樓梯，另記移動途中及到層後樣本，觀察訊號會不會提前或延後變化。

## 6. 第一版模型與前處理

建議先建立可解釋 baseline，不先引入大型模型。可比較「每層代表指紋／centroid」與「k-NN」；用獨立驗證結果決定是否增加其他模型。

1. 凍結 AP 特徵順序與詞彙表；新 AP 不可悄悄插入改變模型維度。
2. 僅使用新鮮、有效的訊號；移除不合理數值並記錄資料品質。
3. 對未偵測建立 missing mask。若採弱訊號填補，值與距離計算規則須由訓練資料決定並記錄，不用 0 dBm 或資料集 sentinel 直接當物理量。
4. 頻段、AP 出現率、強度及相對排序可作候選特徵；效果由分離測試決定，不預設哪種一定最佳。
5. 需要標準化、AP 篩選、缺失填補或調參時，只在訓練集估計；先切資料，再建立所有前處理。
6. 輸出候選樓層、支援證據及 `unknown`。已知 AP 重疊過低、兩候選接近、輸入品質不足時拒絕判斷。
7. 模型、AP vocabulary、前處理、樓層映射及閾值鎖在同一版本包；不能只替換其中一檔。

k-NN 的票數或相似度 margin 可以作工程分數，但未校準前不能顯示為「有 95% 機率人在 B2」。閾值、k、樣本數及運算預算須量測；沒有資料前不承諾準確率、延遲或估時。

## 7. 防止誤切樓層的決策層

分類器輸出與採用結果分開。建議決策狀態為：

```text
disabled／unsupported
  → collecting
  → candidate(floor)
  → stable(floor)
  → stale／unknown（資料過期、訊號不足或矛盾）
```

建議規則，參數待實測定案：

- 同時要求一定的新鮮獨立觀測及持續時間，避免一筆強訊號就換層。重複讀同批 cache 不算新的證據。
- 新樓層採用門檻與維持原樓層門檻分開，加入 hysteresis；避免邊界抖動。
- 觀測超時後撤銷「穩定推測」狀態，標示過期。不能因目前沒有新資料就永遠維持高信心。
- 檢查路網可行的樓層轉換與目前跨層上下文，但路線預期只能作先驗，不能把預期目標直接當感測答案。
- 出現非預期跳層或 Wi-Fi 與新 QR 矛盾時，顯示不確定／需要重掃；不為了配合預定路線強制分類。
- 保留手動檢視樓層；使用者手動切圖時，暫停自動搶回畫面，直到明確恢復跟隨。不能因切圖而改變估計或位置。

穩定判斷會增加換層延遲，必須一起評估「少誤切」與「多久才切」，不能只展示靜止狀態 accuracy。

## 8. 原生與 Web 的候選介面

以下為未實作介面草案；`wifi_floor_session` 不是 TownPass 既有內建功能，也不直接沿用無 requestId 的舊 `location` 協定。

```text
Native scan adapter
  → raw scan observations（裝置本機處理）
  → fingerprint preprocessing
  → FloorEstimator
  → FloorDecision（新鮮度、穩定性、衝突）
  → NavigationController／地圖顯示
```

可採 capability probe、明確 start／stop、sessionId、遞增 seq 及有型別的 status／error。先取得平台能力，不因開頁就請求定位權限；同意並開始後才啟動採樣。若以 Web 分類，限制輸入批次大小、AP 數與頻率，驗證普通數值及已支援欄位。

建議估計結果至少包含：

| 欄位 | 語意 |
| --- | --- |
| `source` | `wifi_live`／`recording_replay`／`synthetic`，不能混稱 |
| `site_id`、`floor_id` | 未知 floor 為 null；必須對應正確場域與支援樓層 |
| `status` | collecting／candidate／stable／unknown／stale／unsupported／permission_denied 等 |
| `observed_at`、`received_at` | 區分量測與收件；時間基準需定義，不直接相減不同時鐘 |
| `session_id`、`seq`、`scan_id` | 去除舊工作、重複資料及晚到結果 |
| `model_version`、`feature_version` | 保證前處理與模型匹配 |
| `score_type`、`score` | 選填，明確說明工程分數，非自動等於機率 |
| `quality`、`reason` | 可用 AP 數、重疊程度、拒絕或過期原因 |

Android last-seen 時間為自開機起算，不能當 Unix time；跨 bridge 可傳明確單調時間／年齡與該次 native session 識別。App 重啟後重設基準，不能把不同開機期間的數值直接比較。

原生端核對 main frame、可信 origin、能力與生命週期；停止、卸載或重新開啟後丟棄舊 session 回覆。共享資料盡量留在本機；若只需估計結果，評估不把原始 BSSID 暴露給所有頁面。

## 9. 與導航、持續掃碼及集合點整合

### 9.1 三種狀態分開

| 狀態 | 來源 | 可以改變什麼 |
| --- | --- | --- |
| `confirmedLocation`／目前程式 `state.position` | 經有效 QR 流程採用的 anchor | 導航起點、定位時間及完整重算 |
| `floorEstimate` | Wi-Fi 推測及觀測時間 | 顯示候選／穩定樓層，第一階段不提供精確 node |
| `displayFloor` | 使用者檢視或自動跟隨 | 切換地圖，不代表感測位置或抵達 |

上述是責任概念與候選名稱，不表示現有程式已宣告全部欄位。QR 記錄為「上次確認位置」，Wi-Fi 顯示為「推測樓層」，資訊過期時各自標示；不把舊 QR 標點畫在新樓層的相同 x/y。

### 9.2 與目前持續掃碼並存

目前 [集合點與持續掃碼指南](./集合點與持續掃碼開發指南.md) 已有目的地優先、有效 QR 自動更新、`qr_scan_session` 與 guidance token 設計。Wi-Fi 不取代這個有效 anchor 更新流程。

- 新 QR 與 Wi-Fi 衝突時，保留已查核的 QR 位置並使矛盾估計失效／待確認，不用 Wi-Fi 偷偷覆寫 anchor。QR 仍有實體移貼等限制，衝突不能當成任何來源絕對正確的證明。
- 在原生掃碼頁保持開啟時，若要讓 Wi-Fi 自動切圖也影響原生指引，必須另設明確資料同步。只更新 WebView 地圖不代表被原生相機覆蓋的使用者看得到。
- Wi-Fi 事件不能觸發舊 guidanceToken 的「下一步」，也不能把感測事件偽裝成使用者已按確認。
- 結束導航、退出服務、權限撤銷或停用選配功能時，停止／清理本實驗的訂閱與資料，不能破壞原本相機 channel。

### 9.3 第一階段只自動切圖

穩定辨識 B2，只代表推測在 B2；不知道是某座電梯口、某個樓梯口，或同層其他位置。因此不得據此自動：

- 建立精確 node、移動定位藍點或從猜測落點重算。
- 認定已離開電梯、確認出口朝向或任意推進指引。
- 判定抵達集合點、找到朋友，或更新分享者的固定集合連結。
- 放寬無障礙、方向、付費區或封閉邊限制。

可用它提示「推測已到目標樓層」並自動顯示對應地圖；錯誤或 unknown 時保留手動／QR 流程。

### 9.4 第二階段才研究自動確認到層

SPEC 目前仍以 manual／qrOrManual 確認指引，本次提案沒有新增 `sensorAutomatic`。若要取消到層按鈕，需先定義可適用 connector、目標層、新鮮度、穩定性、誤判與最大延遲門檻，並在真實跨層測試通過後調整狀態機、原生指引與測試。

樓層判斷正確也不保證已到可安全轉向的位置。自動到層不等於自動朝向確認，未知設備／方向不可藉模型分數放行。

## 10. 模擬及 DEMO 的證據層級

| 模式 | 實際工作 | 可以說明 | 不能宣稱 |
| --- | --- | --- | --- |
| UI 模擬 | 按鈕或時間表切換樓層 | 地圖顯示與操作構想 | 有訊號分類器或定位成效 |
| 合成訊號 | 人工生成 RSSI、缺失、雜訊，讓模型與決策器處理 | 程式、邊界與假設下的行為 | 北車 RF 環境或實際準確率 |
| 實測資料回放 | 將既有真實 RSSI 送入實際分類器 | 該資料場域上的模型效果 | 正在讀現場訊號、已支援北車或一般 iOS |
| Live Android | 真機掃描並分類，配真實樓層標註 | 已測裝置、場域與條件下的能力 | 全站、全裝置、全時段可靠 |

回放輸入只能提供模型可用特徵；真值樓層保留在評估器。資料中的 label、檔名或播放順序不得偷偷成為分類答案。

可先做獨立實驗頁，顯示真值／預測、輸入來源、新鮮度、穩定狀態與切層事件。用其他建築資料時，顯示該測試建築的樓層或合成圖，不直接把它標成北車 B1／B2 實際定位。實驗診斷和正式使用者指引分開呈現。

## 11. 評估方法與成功門檻

### 11.1 切分與避免洩漏

- 先分訓練／驗證／最終測試，再建立前處理及調閾值；最終測試不反覆用於調參。
- 同一時間連續採到的近似指紋，依量測 session／軌跡分組，避免隨機拆到兩邊。
- 另測不同裝置、區域與時間；所有待辨識樓層需有合理訓練覆蓋。
- 只有官方既有 split 可用時先使用並揭露其限制；不能假定它已覆蓋北車或所有裝置差異。
- 模型不能只靠目前預定路線猜目標層。加入「沒有換層」及「非預期換層」測試。

### 11.2 不只看 accuracy

| 指標 | 為什麼需要 |
| --- | --- |
| 逐層 confusion matrix、macro-F1 | 找出相鄰樓層混淆，避免多數層掩蓋失敗 |
| unknown／拒絕比例及 accepted coverage | 防止全回 unknown 卻宣稱零誤判 |
| 已採用結果的錯誤率 | 模型真的採用時有多常錯，需與 coverage 一起報 |
| 同層停留的誤切次數／時間 | 比單筆分類分數更貼近地圖體驗 |
| 換層至穩定採用的延遲分布 | 包含等掃描、觀測、分類及決策，不只計算模型毫秒數 |
| 掃描成功率、新鮮批次間隔及資料年齡 | 分辨平台瓶頸與模型瓶頸 |
| 不同裝置／時間／區域表現 | 檢查部署泛化能力 |
| 耗電與持續操作表現 | 決定是否適合實際開啟 |

量測前由團隊約定可接受的誤切、延遲、coverage 與運算預算；目前沒有實測，因此不先填「準確 95%」「一秒內換層」等承諾。若沒有真實跨層序列，延遲欄位填 not_run，不由獨立樣本推估成真機結果。

## 12. 主要隱患與控制

以下為工程風險分析，不是已發現漏洞或已量測的發生率。

| 隱患 | 可能結果 | 建議控制／驗證 |
| --- | --- | --- |
| 相鄰層訊號重疊、挑空／樓梯井傳播 | 提前或錯誤切層 | 分區測試、跨層序列、unknown、穩定決策 |
| 電梯內外訊號差異與掃描延遲 | 尚未到站就切圖，或到站很久才切 | 到層前後停留測試；不先自動推進 |
| AP 維護、換機、功率或配置改變 | 舊模型失效 | 模型日期、AP 重疊監控、停用與重蒐 |
| 手機、持握、方向、身體遮蔽、人流差異 | 同層分數漂移 | 跨裝置／方向／時段驗證，不只測開發機 |
| Cached scan 被重複算成新證據 | 虛假穩定、高信心錯切 | last-seen、scan ID、新鮮度與時間基準驗證 |
| 陌生場域仍強制給樓層 | 到其他建築卻顯示北車樓層 | site gate、AP 覆蓋、out-of-distribution 拒絕 |
| 新模型搭配舊特徵表 | 分類無聲錯誤 | 整包版本鎖定、hash、載入驗證 |
| 回放／真值洩漏 | DEMO 漂亮但模型沒學到訊號 | 分離輸入與 label，獨立資料切分 |
| 把工程 score 當機率 | 使用者過度信任 | 分數定義、校準或改用可解釋狀態 |
| 樓層推測冒充精確位置 | 錯誤重算、集合點資訊失真 | QR／estimate／display 分離，禁止生成假 anchor |
| 多來源及晚到事件競態 | 舊樓層覆蓋新 QR、新指引被跳過 | session／seq／revision、來源衝突規則及回歸測試 |
| AP 名稱／身分被仿冒 | RSSI 模式誤導 | 不把 RF 分類當身分或安全保證，保留地標與 QR 核對 |
| 平台或權限不支援 | 服務卡住或使用者被迫授權 | capability、可取消權限、手動／QR 備援 |
| 模型探索排擠核心 | 七語、導航與穩定性未完成 | 獨立試作範圍及停止條件 |

## 13. 資料、隱私、授權與離線

Wi-Fi 量測可能揭露 AP 與室內活動位置，不能把「公開可見」視為完全沒有資料處理責任。第一版以使用者主動啟用、前景取樣及裝置本地推論為原則；預設不收帳號、人物身分或持續軌跡，也不自動上傳掃描清單。

研究資料另訂蒐集目的、保存／清除及再散布範圍。裝置用匿名研究代碼；BSSID 單純 hash 仍可能可連結，不等於完成匿名化。若採本地 AP 映射，須保持特徵一致並評估其公開風險。

模型、資料、字型、套件、native plugin 及衍生資產仍須遵守既有非中國來源與權利審查，新增時更新第三方紀錄。候選資料、學長程式或 GitHub repo 不能只因免費／開源就自動核准。

本地模型可不呼叫雲端推論，但還需模型與資料包預載；關網、Wi-Fi radio 關閉、飛航模式及重新開啟 Wi-Fi 是不同測試。無可用掃描就回退，不宣稱所有離線情境都能 Wi-Fi 定位。演算法回放離線成功，也不代表 live 掃描或首次安裝離線已通過。

## 14. 分階段試作、交接與停損

| 階段 | 工作 | 產出與退出條件 |
| --- | --- | --- |
| A：能力探查 | 確認資料權利、Android 裝置及可用 API | 能取得新鮮 scan；失敗時記錄權限／限制，不先做自動切圖 |
| B：離線 baseline | 資料切分、前處理、centroid／k-NN、unknown | 可重現的測試與錯誤案例，不把 score 包裝成機率 |
| C：決策器 | 新鮮度、去重、hysteresis、穩定／過期 | 同層及換層序列結果，明確 trade-off |
| D：獨立實驗頁 | Live／replay adapter 與診斷呈現 | 來源可辨，不影響原導航；無真機時明說 replay |
| E：輔助切圖 | 合法 floor mapping、手動 override、QR 衝突處理 | 圖可自動跟隨且位置／路線不被偽造 |
| F：到層自動確認研究 | 依限定 connector 與驗收門檻調整 SPEC | 另行決策；資料與實機證據不足則不啟用 |

可讓一位組員探索，其餘人繼續導航、七語與集合點主線。探索時間上限由團隊依剩餘工時約定；本文件不承諾幾小時能完成。

停止擴大的條件：沒有可用資料／權利、真機只能取得過期結果、iOS 被要求與 Android 同等任意掃描、穩定決策後仍頻繁誤切、只有合成或單一裝置佳績、開始影響核心交付。停止整合仍可保留清楚標示的研究成果，不勉強包裝為正式功能。

建議交接產物：資料來源與欄位說明、split 清單、前處理／模型／閾值版本、可重現訓練與評估方式、scan adapter 能力報告、失敗案例、實驗頁操作、真機環境與 not_run 清單。程式檔案位置由實作者決定，不因本文而預建空目錄或加入依賴。
