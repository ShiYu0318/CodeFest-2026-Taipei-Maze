# Taipei Maze｜掃碼分享集合點功能提案

更新日期：2026-11-07｜版本：討論稿 0.1｜狀態：僅完成提案整理，尚未實作或排入正式交付

> **一句話：A 掃碼確認站內位置，分享一個明確的集合點；B 點開查看，抵達車站後掃自己的 QR，再用適合自己的語言與通行需求前往。**

本文依使用者提出的構想與後續討論整理，供團隊確認後決定是否開發。文件新增已獲授權；功能排程、資料欄位、連結格式與宿主修改仍屬建議，不代表已逐項定案。本文不修改或覆寫 [SPEC](./SPEC.md) 的 P0／P1、資料契約及驗收門檻，也不表示官方要求開發此功能。

## 1. 問題、想法來源與服務價值

「約在台北車站」缺乏足夠的位置資訊。雙方可能位於不同樓層、不同營運區域，或站在同名設施旁；口頭說「我在電梯附近」仍難以會合。外籍旅客也可能無法描述或辨認中文標示。

使用者提出：既然 QR Code 對應站內一個固定位置，A 掃碼後即可生成連結，自行分享給 B，讓 B 知道應該到哪裡找 A。

功能的完整價值包含兩段：

1. **說清楚在哪裡集合：** 用樓層、定位點、現場地標與局部圖，取代模糊描述。
2. **協助接收者走到集合點：** B 掃自己的定位碼後，沿用導航引擎規劃到集合點的路線。

同一個集合點可由不同語言介面呈現；A 的語言與通行偏好不應強制套給 B。B 可以閱讀自己的語言，並選擇符合自身需求的路線。

## 3. 位置語意與產品界線

### 3.1 連結代表什麼

連結代表「A 在某次掃碼並確認後，選定的固定集合點」。它不能證明 A 此刻仍在那裡，也不自動證明分享者身分。

建議名稱為「掃碼分享集合點」；使用者按鈕可用「在這裡等朋友」，接收頁以「集合點」為主標題。避免使用「即時追蹤朋友」「朋友目前位置」等會讓人誤解的名稱。

接收頁可顯示「分享者於〔時間〕掃碼確認此位置，請先確認對方仍在這裡等候」。時間來自分享端裝置，未經伺服器驗證時只作參考，不宣稱是可信即時狀態。

### 3.2 三個不同時間

| 時間 | 意義 | 注意事項 |
| --- | --- | --- |
| 掃碼確認時間 `confirmed_at` | A 最近一次確認此 anchor 的時間 | 分享時不得直接改成現在 |
| 連結產生時間 | A 按下產生連結的時間 | 較新的連結不代表重新定位 |
| B 開啟時間 | B 在自己裝置查看的時間 | 不證明 A 有更新或正在等待 |

A 若已離開定位點，應重新掃碼後分享。相同靜態連結不會自動更新；傳送新集合點時需告知對方以新訊息為準。

### 3.3 第一版不包含

- GPS／藍牙連續定位、A 的移動軌跡或背景追蹤。
- 帳號、好友列表、內建聊天、已讀、對方在線或自動會合偵測。
- 跨裝置同步 B 的進度給 A，或自動通知 A「朋友已到」。
- 任意點地圖就宣稱為已掃碼位置。
- 全北車覆蓋、任意付費區穿越、即時人流或設備狀態。
- 執行期 LLM、翻譯或 TTS API。

## 4. 使用流程

### 4.1 A：產生與分享

1. 從城市通開啟服務，掃描本專案支援的站內 QR。
2. 依既有流程確認定位點、樓層、現場地標與時間。
3. 系統查核 anchor 是否啟用、版本是否相容，以及此點是否允許作集合點。
4. A 按「在這裡等朋友」，查看集合點卡與上次確認時間，確認自己仍在此處並會留在此處等候；若已移動，先重掃。
5. 產生固定連結，由 A 自行選擇分享方式；顯示分享選單失敗時，仍可複製連結或查看集合資訊。
6. 分享後保留集合卡供 A 對照；不顯示未經驗證的「B 已收到／已讀」。

若掃碼點不適合作集合，第一版不開放以該點分享，也不自動改成附近別的位置。未來可引導 A 前往核准集合點，抵達後重新掃碼確認再分享。

### 4.2 B：查看與導航

1. B 點開連結，服務先驗證連結版本、場域、集合點與本地資料相容性。
2. 顯示集合點名稱、樓層、中文現場標示、局部圖、定位確認時間與非即時提醒。
3. B 可選自己的語言；單純查看集合點不要求帳號、GPS 或相機權限。
4. B 按「帶我到集合點」，系統檢查是否在支援掃碼的城市通環境。
5. 在城市通內掃 B 附近的 QR，確認 B 的起點及出發朝向；一般瀏覽器沒有 bridge 時，顯示開啟城市通的說明或備援方式。
6. B 選擇自己的通行需求，沿用核心引擎規劃到集合點的路線。
7. 途中可重新掃碼；重算時保留集合目的地與 B 的需求。
8. 抵達由 B 手動或有效目的地 QR 確認；介面顯示「已抵達集合點」，雙方自行確認是否找到彼此。

### 4.3 特殊情況

| 情況 | 建議行為 |
| --- | --- |
| B 還沒到車站 | 可以先查看集合資訊；尚無可靠起點，不提供站內路線 |
| B 已在導航其他目的地 | 先詢問是否切換到集合點，不因開連結就覆蓋原任務 |
| B 的上次掃碼後已走動 | 開始新會合任務先重掃，不以舊步驟推測位置 |
| A 與 B 在同一節點 | 進抵達確認，不生成虛構行走指令 |
| B 無法走到 A 的集合點 | 說明無符合需求路線；請雙方另約可達集合點，不放寬無障礙條件 |
| A 已離開但沒重傳 | 舊連結仍指向原地；提醒 B 自行與分享者確認，不能自動得知 A 已離開 |
| B 重新開啟連結 | 重新驗證集合點；不自動恢復成正在導航或認定仍在上次起點 |

## 5. 集合點資料與場域條件

### 5.1 不讓所有 QR 自動成為集合點

第一版建議只挑少量位置明確、可辨識、適合等候的點，先驗證兩個不同集合點。不得阻擋樓梯、電扶梯、閘門、電梯門、通道或疏散動線；正式使用仍需管理單位核對與同意。

只靠平面圖或熟悉台北，無法證明現場等待空間適合。只能遠端核對時，保留 `desk_checked`／示意狀態，不改標 `field_checked`。展示環境與真實站內導航依 SPEC 的驗證模式區分。

### 5.2 建議新增 MeetingPoint 資料

以下是建模提案，尚未加入 schema、資料檔或正式包。

| 欄位 | 用途與限制 |
| --- | --- |
| `id` | 穩定集合點 ID，與 QR anchor ID 分開命名 |
| `site_id` | 明確場域，避免同樓層名跨場域誤認 |
| `anchor_id` | A 實際掃碼確認的定位點 |
| `destination_poi_id` | 預先登錄的導航目的地 POI |
| `name_key`、`original_signage` | 七語名稱與現場原文對照 |
| `waiting_guidance_key` | 指定等候位置的簡短說明 |
| `enabled`、`shareable` | 是否仍有效、是否允許產生分享連結 |
| `waiting_area_status` | `approved`／`unsuitable`／`unknown`，僅核准者用於實地服務 |
| `verification_status`、`source_ids` | 沿用既有核對狀態與來源追溯 |

樓層、座標與導航節點應由 anchor／POI 的引用推導，避免重複保存後不一致。第一版要求 anchor 與集合目的地對應同一個核准節點，不能掃在 A 點卻默默分享成隔壁 B 點。

### 5.3 與現有 POI 契約的銜接

SPEC 目前以 `destinationPoiId` 表示導航終點；不能直接把任意 `anchor_id` 塞進這個欄位。建議以 MeetingPoint 映射到預先登錄的 POI，再交給既有 RoutePlanner。

若需要新增 `meeting_point` POI 類別，須同步討論 SPEC、validator、七語分類、圖示與測試；不把它偽裝成廁所或電梯。另一種作法是擴充正式目的地型別，但會影響較多模組，應先評估再決定。

集合點可被分享，不代表對每位 B 都可達；可達性取決於 B 的起點、通行需求、允許區域及有效路網。第一版宜沿用 SPEC 公共示範區範圍，不因會合而開放跨付費區。

## 6. 連結格式與驗證：建議方案

### 6.1 第一版採固定連結，先不做會合後端

建議使用正式 HTTPS 網域下的 `/meet` 頁面，連結只帶足以查詢靜態集合點的識別資訊。不需要為每次分享建立伺服器上的人物或位置紀錄。靜態頁仍需要可用的部署入口，不能把 localhost／127.0.0.1 發給另一台手機當成正式連結。

下例僅供討論，網域、路由、ID 與時間皆為示例，尚不可操作：

```text
https://example.invalid/meet?type=taipei_maze_meeting&v=1&site=taipei_main_demo&point=mp_b1_a&graph_major=1&confirmed_at=2026-11-07T16%3A30%3A00%2B08%3A00
```

| 欄位 | 建議用途 |
| --- | --- |
| `type`、`v` | 區分集合點分享與其他 payload，辨識格式版本 |
| `site` | 查本地已支援場域 |
| `point` | 查 MeetingPoint ID，再解析到已核准 anchor／POI |
| `graph_major` | 主要路網相容性；minor／patch 仍需查核點位語意與有效性 |
| `confirmed_at` | 顯示分享者最後掃碼確認時間；不作身分或真實位置證據 |

不在連結接受任意座標、樓層、HTML、導航指令或外部圖檔；名稱、樓層、地標與可及性均從已核對資料取得。A 的姓名、電話、帳號、裝置 ID、精確 GPS、B 的路線需求也不需要放入。

### 6.2 解析與相容性規則

- 建立獨立的 MeetingLink parser；格式與長度上限需定案，例如總長度 2048 bytes 的工程預設。拒絕重複參數、錯誤型別、未知版本、非法 ID 及無效時間，不以參數順序決定結果。
- 點位必須存在、啟用且允許分享；跨場域、已停用或不相容路網均不開始導航。不同 major 不自行猜對應；點位 ID 不得被重用為不同位置。
- 開啟完整 URL 時僅接受核准的 HTTPS origin／路徑；在 App 內匯入時同樣驗證，不把任意網址交給 `open_link`。
- **站內 anchor QR 與分享連結是不同輸入。** 掃到集合分享碼不能當成「B 位於集合點」；只能載入目的地，B 仍需掃實體定位碼確認起點。
- 連結時間可被修改、裝置時鐘也可能不準。過舊或未來時間顯示重新確認提示，門檻待定；不宣稱已驗證 A 此刻仍在場。

### 6.3 固定連結的更新、期限與撤銷

第一版沒有即時後端時，A 不能透過一個按鈕撤銷別人已保存的連結，也不能讓舊連結跟著自己移動。若加入有效時間，只能先作介面上的過期提示；不是不可繞過的存取控制。

真正的短連結、單次使用、到期、撤銷或同步更新，需要額外服務、權限與維護方案，留待後續另案評估。資料包停用某集合點與撤銷某次分享不同；舊離線包也不會立即知道新的停用資訊。

## 7. 分享方式、瀏覽器與城市通整合

| 環境／能力 | 設計方向 | 未驗證部分與備援 |
| --- | --- | --- |
| A 觸發分享 | 使用者按鈕觸發系統分享；Web Share API 為候選 | 不假設所有 WebView 支援；提供複製或可選取文字 |
| 複製連結 | Clipboard API 為候選 | 權限或平台限制時，顯示可手動複製的連結 |
| B 一般瀏覽器 | 查看靜態集合資訊、局部圖與語言切換 | 無 `flutterObject`，不偽造原生掃碼 |
| B 城市通內 | 以 `qr_code_scan` 取得 B 自己的起點 | 沿用單一在途、取消、逾時與遲到回覆規則 |
| 外部連結帶入 App | Universal Links／Android App Links 或自訂入口僅為候選 | 尚未核對宿主與正式網域能力，可能涉及原生設定 |
| App 內輸入集合資訊 | 若不能自動帶入，可評估「貼上集合連結」再走同一 parser | 新 UI 仍需實作測試；不自動讀取剪貼簿 |

網站分享頁先可讀、城市通導航再銜接，能降低 B 的進入門檻；是否能做到無縫跳轉，需要專門驗證，不能把一般瀏覽器開頁當成城市通整合完成。

分享給 LINE 等平台由使用者自行操作；第一版不建置自動傳訊或要求通訊錄。連結與預覽可能被轉傳，使用者應知道持有連結者可查看集合資訊。查詢參數也可能出現在瀏覽紀錄、伺服器或訊息平台紀錄，因此不能宣稱整個分享過程沒有任何外部留痕；正式部署應減少日誌並避免非必要追蹤及詳細預覽資料。

## 8. 導航、多語與狀態一致性

### 8.1 沿用導航，不建立第二套定位

集合點是 B 的目的地，不是 B 的 `confirmedLocation`。A 的確認時間只作集合資訊，不能寫入 B 的定位紀錄。B 的起點取自自己的有效 QR；B 的 mobility profile、語言、簡易模式及靜音沿用自己的設定。

開連結先建立「待確認集合目的地」，確認後才替換 active destination。路徑成功、方向指引可用後才開始導航；路網可達但缺朝向指引時，依 SPEC 顯示指引尚不可用，不能猜左右。

沒有符合 B 需求的路徑時回 NoRoute；不自動改一般模式、不逆行電扶梯、不突破區域或未知可及性限制。重掃後須失效舊路線及音訊，再提交新計畫。

### 8.2 七語與現場對照

新增頁面、按鈕、錯誤與集合點名稱均納入既有七語 catalog：`zh-TW`、`en`、`vi`、`id`、`th`、`ko`、`ja`。連結分享同一個點位 ID；B 的介面語言自行決定，不強制跟隨 A。

現場中文標示、設備與出口編號保留作對照。資訊包括「分享者確認時間」「非即時位置」「先掃自己的定位碼」「找不到符合需求路線」等，不能只翻譯成功畫面。

固定新增文案可在開發期翻譯，遵守既有來源與校對要求。導航沿用預生成音檔；不即時念出任意分享內容或呼叫 TTS。若需新增語音句，另評估七語資產與驗收，不把它算進現有 168 個核心音檔已涵蓋的能力。

### 8.3 保存與生命週期

依 SPEC，導航 session 結束後清除記憶體中的位置與路線；第一版不新增位置歷史或「朋友位置」持久列表。語言、模式與靜音仍按既有規則保存。

重新開服務可由使用者再開原連結或明確貼上；不得默默恢復成 A 或 B 仍在原點。使用者已複製、傳送的連結不受本地 session 清除影響，需清楚區分。

## 9. 離線能力與失敗恢復

| 情況 | 可以承諾的能力／恢復方式 |
| --- | --- |
| 產生連結 | 已有有效本地資料與定位時，可在本機組合字串；分享選單本身依平台驗證 |
| 傳送連結 | 是否送達取決於外部通訊工具及網路，不宣稱完全離線傳送 |
| B 首次開一般 HTTPS 分享頁 | 沒有網路、快取或本地封裝時不能保證載入 |
| B 已有完整宿主離線包 | 還需有經驗證的本地輸入／連結匯入方式，才可能離線查點與導航 |
| 點位不存在、停用或版本不符 | 不畫猜測位置，提示重新取得連結或回到一般目的地選擇 |
| 分享失敗或使用者取消 | 保留集合卡，不謊稱已傳送；可再試或複製 |
| 相機權限拒絕或掃碼取消 | 保留集合目的地；說明如何恢復，不虛構 B 起點 |
| 無路線、核心資料或地圖錯誤 | 停止不可用導航；提供集合文字供自行問路，避免錯誤方向 |
| 音檔缺失 | 保留文字與圖像，揭露語音狀態 |

「固定分享不需即時位置後端」與「整個跨裝置流程完全離線」是不同承諾。首次離線仍須符合 SPEC 的宿主 bundle 與實機驗證要求。

## 11. 五面向與競賽價值

| 面向 | 功能價值 | 需要的證據 |
| --- | --- | --- |
| 可行性 | 重用 QR、地圖與路網，固定分享可先不加帳號及即時後端 | 兩台手機能開同一集合點；可重建部署與資料 |
| 功能性 | 完成「描述位置 → 朋友理解 → 從自身起點前往 → 抵達」 | A、B 不同起點的完整流程 |
| 可靠性 | 節點引用可驗證，失效／未知／不可達可明確拒絕 | 版本、錯碼、NoRoute、取消與重掃案例 |
| 易用性 | 少打字，樓層與原文標示清楚，支援個別語言與需求 | 初次使用者理解集合卡與第一步方向 |
| 亮點巧思 | 同一集合點，雙方各用自己的語言及可走路線會合 | 跨語言、不同通行需求實機示範 |

依本地競賽指南，這個情境可支撐初選服務應用與清楚介面，決選則能展示情境完整度、落地及穩定性；這是評分對齊分析，不保證加分或晉級。官方入門指引的「便利、透明、有感、安全」可分別由入口銜接、位置時效說明、會合任務與少蒐集資料回應。

建議展示主題：「朋友在北車等我，我用自己的語言與通行需求，找到同一個集合點。」不用簡報或預錄動畫偽裝即時操作，沿用官方實際作品展示要求。

## 12. 分期建議與停損

| 階段 | 工作 | 完成條件 |
| --- | --- | --- |
| 前置 | 完成核心 QR、有效局部路網、導航與重掃，選定核准集合點 | 能可靠提供起點與終點，資料有核對狀態 |
| 第一段 | A 確認集合卡、產生／複製連結；B 瀏覽器查看 | 兩台裝置看見同一樓層、點位與地標；僅能稱分享查看完成 |
| 第二段 | B 在城市通匯入目的地、掃自己的 QR、導航與抵達 | 不同起點會得到對應路線，保留 B 的需求 |
| 第三段 | 七語、簡易模式、錯誤恢復、生命週期與雙平台 | 測試結果、版本與限制可查 |
| 後續候選 | 分享碼圖像、更多集合點、問路卡整合、受控場域試辦 | 核心穩定、有可靠資料與來源許可 |

若只能完成分享頁，展示時明說尚未接上導航。核心 P0 未穩定前，不為此功能增加聊天、追蹤、短網址、會員或同步後端；也不犧牲七語、無障礙硬限制與路線正確性。

## 13. 建議驗收案例

以下全部為待執行案例，不是 PASS 紀錄。測試應記錄 build、資料版本、裝置／OS、語言、條件、預期、實際與證據。

| ID | 情境 | 必須觀察到的結果 |
| --- | --- | --- |
| MEET-01 | A 掃有效碼並選擇集合 | 名稱、樓層、地標與 anchor／POI 對應正確 |
| MEET-02 | A 過了一段時間才分享 | 保留原掃碼確認時間，不以產生連結時間冒充新定位 |
| MEET-03 | 點位不適合等候或未核准 | 不開放實地集合分享，不自動換別的位置 |
| MEET-04 | 兩台手機開啟連結 | 對應同一個固定集合點；尚未取得 B 的起點 |
| MEET-05 | A 中文、B 英文或其他支援語言 | 點位不變，B 呈現自身語言並保留現場原文 |
| MEET-06 | B 無城市通 bridge | 可看集合資訊；不假稱掃碼成功，有明確進入／匯入說明 |
| MEET-07 | 分享／剪貼簿不支援或取消 | 可恢復或手動複製，不宣稱對方已收到 |
| MEET-08 | 錯誤 URL、重複參數、超長、未知 site／point／major | 拒絕或顯示版本提示；不接受任意座標或外部跳轉 |
| MEET-09 | 已停用點位、過舊或未來時間 | 顯示對應限制，不宣稱 A 現在仍在該點 |
| MEET-10 | B 掃自己的有效 QR | 只更新 B 的 confirmedLocation，集合點保持為終點 |
| MEET-11 | B 掃到集合分享碼而非定位碼 | 不把集合目的地寫成 B 起點；依不同入口拒絕或僅載入目的地 |
| MEET-12 | B 開無障礙需求、只有樓梯可達 | NoRoute，不回退一般模式；集合點可分享不等於人人可達 |
| MEET-13 | B 正在其他任務時開連結 | 確認後才切目的地，取消則保留原任務 |
| MEET-14 | B 重掃、取消、拒權、bridge 遲到回覆 | 依 SPEC 恢復；不混用新位置與舊路線，不播過期音訊 |
| MEET-15 | A 離開或產生新連結 | 舊連結仍為原集合點；沒有假更新、撤銷或在線提示 |
| MEET-16 | B 同起終點或到最後一步 | 需確認抵達集合點，不宣稱系統已辨識 A 本人 |
| MEET-17 | 首次 HTTPS 關網、已有本地包關網 | 分開記錄；本地包須測匯入方式，不能混稱完整離線分享 |
| MEET-18 | 七語長文、大字、音檔缺失、背景與返回 | 主操作可達、定位語意不變、圖文可用、不誤播 |

使用者觀察可比較「口頭描述位置」與「集合卡＋導航」的理解、求助與完成情況；遠端測試只說明介面理解，不外推實際北車行走效果。小樣本揭露條件，不宣稱零迷路或提高特定百分比。
